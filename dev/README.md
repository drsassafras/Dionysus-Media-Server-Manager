# Developing Dionysus

This folder holds what you need to try changes on a real TrueNAS before pushing them:

| File | What it is |
|------|------------|
| `compose.dev.yaml` | A **test copy** of the app (`plex-cache-dev`, port 8643) that runs the published image but with its code replaced by whatever you last copied to the NAS. It has its own settings, so it never touches the real `plex-cache` app. |
| `future.py` | Builds the image on the **next** Python's prerelease (3.16 while the image runs 3.15) and each tool's newest pre-release where one is ahead of its stable release (Node's nightlies, ffmpeg's git snapshot, libjpeg-turbo's and oxipng's pre-releases, the web's npm packages' `next`/`beta`/`rc` tags; MKVToolNix has releases only), and runs the suite inside it, every warning an error and the web's checks a year ahead (four years of browsers); `--stable` keeps the tools at their pins, `--local` uses an interpreter on your computer instead. The "future" track, local only (below). |
| `upkeep.py` | The dependency check: everything the app depends on against upstream's newest release, pins a minor behind moved (only with `dev` checked out), a major behind a prompt. callboard runs it on every run (below), with a progress bar for each look-up and npm install; the suite's test reads its last answers, never upstream or npm. |
| `cves.py` | The dependency check's CVEs (`upkeep.py` runs it, alongside the versions): what needs doing only, always a warning. See **Known vulnerabilities** below. |
| `versions.py` | Prints what an image carries (its OS, Python, MKVToolNix, ffmpeg…); each build logs it. |
| `codecs.py` | Codec names as MKVToolNix shows them, for Library Health (`plexcache/codec_names.py`). The image build runs it for the MKVToolNix release it installs; run it by hand to refresh the committed copy. |
| `web.js`, `package.json`, `jsconfig.json`, `web.d.ts` | What checks and builds the web app's CSS, scripts and pages: **Stylelint**, **ESLint** and **html-validate** on the source (each with a check that no feature it uses is missing from a target browser), **TypeScript** on the scripts (checkJs), **axe-core** on every page as the demos draw it (through **Playwright**), then **postcss-preset-env** (the newer CSS its targets lack, rewritten as CSS they read), **Autoprefixer** (the browser prefixes they need), **cssnano**, **Terser** and **html-minifier-terser** (minified) for the image. The settings, the browser floor and the pinned packages are in `package.json`; see below. |
| `screenshots.js` | Makes the README screenshots from the demo (see below). |
| `icons.js` | Draws the app's icons in Chromium, as a browser draws them, each from the logo the app shows at that size and centred on what it draws: `favicon.ico` from the tab icon (`plexcache/web/theatre-tab.svg`: Joined D at 16px, Wide bar at 32 and 48px; for browsers without SVG favicons), and from the full theatre playing (`theatre-playing.svg`, the menu's logo with its arrow lit) on the menu's colour the iPhone's `apple-touch-icon.png` and the installed app's `icon-192.png`, `icon-512.png` and `icon-maskable-512.png` (`manifest.webmanifest`); and the dev pages' tab icon, the film reel as `decor.js` draws it for a tab (`PCDECOR.tab`: five round holes at 16px, plain columns in the cut ring at 32px, the reel itself from 64px) in Dionysus's film colour with light cutouts, as `dev/reel-tab-*.svg`. Run `NODE_PATH=$(npm root -g) node dev/icons.js` after changing either logo or the reel, then the style sample; `IconTests` fails when one is out of date (`node dev/icons.js check`). Needs Playwright, like the screenshots. |
| `style.py`, `style-guide.json`, `style-sample.js`, `decor-draws.js` | **The style guide**: every look the app may wear, each approved by the maintainer from a sample. `style.py check` lists what's new, changed or gone (the suite fails on it), `sample` photographs those in each theme and mode, `approve` (the maintainer only, at a terminal) adds them. See below. |
| `make_fixtures.py` | Makes the optimizer's test files (`tests/fixtures/*.mkv`: many real-world features, a few hundred KB) and the snapshot of what optimizing them gives. Run it with `--snapshot` after checking a change the tests caught (needs ffmpeg and MKVToolNix). |

**callboard itself is a project of its own** ([github.com/drsassafras/callboard](https://github.com/drsassafras/callboard), checked out beside this one: `~/Code/callboard`), installed once on a computer and used by every project. Its board, rules, check tools and UI used to be files of this folder; what's left here is what's Plex Cache's own, built on it (`dev/__init__.py` finds the install: `CALLBOARD_HOME`, else the `callboard` on your PATH, else `../callboard`). `callboard tool <name>` runs one of its tools in the project you're in (`callboard tool typecheck`, `buildcheck`, `coverage`). In that project:

| File | What it is |
|------|------------|
| `bin/callboard` | A small script that **copies your code to the NAS, restarts the test app and runs the tests and checks** — in one command, from your computer, all at once on a live board (`board.py`). Each run leaves a record that the callboard UI shows (below). |
| `callboard/devui.py`, `devui.html`, `devui.css`, `ui/` | **The callboard UI** (`callboard ui`): the board in your browser, a page behind each block with what its tool found, and buttons that run callboard again. See **The callboard UI** below. It wears the app's themes from a copy of its own (`ui/`, taken again with `ui/refresh.py` when the app's look moves on). |
| `callboard/devpage.py` | What the dev tools' pages share (the UI's, the audits', the style review's): served to this computer only, to the browser that opened the printed address only, closed when the page is; and their tab icon, the film reel (`reel-tab-16.svg`, `-32.svg`, `-64.svg`: one link a size, so the browser takes the one drawn for the size it shows). |
| `callboard/progress.py` | The progress bar the dev tools share, the result line, and `detail`: a tool's own account of what it found, written as JSON for its page in the UI when the board asks (`CALLBOARD_DETAIL`). |
| `callboard/typecheck.py` | **Python Validation**: pyright's type check (`pyrightconfig.json`) and Ruff's lint (`ruff.toml`), each at its version in `tools.toml`, as callboard and GitHub run them; `--fix` makes Ruff's safe fixes first. |
| `callboard/checks.py`, `tools.toml` | **What every check tool shares**: `tools.toml` holds each check tool's version (this project's own `dev/tools.toml` wins over the one callboard ships, so its pins are the ones `upkeep.py` moves) (and, for a release binary, where it comes from and its checksum for each platform); `checks.py` fetches each at it the first time (into `~/.cache/plex-cache/tools/`: `callboard.toml`'s `[config] cache`), says what each finds one way (`file:line:col - severity: message (Tool CODE)`, annotated on GitHub), draws the board's bar and says the result line. A check tool is a section of the board run through it, never one of its own (`CheckToolTests`). |
| `callboard/buildcheck.py` | **Build Validation**: ShellCheck on the project's shell scripts (every one it has; in callboard's own project, `bin/callboard`), actionlint on `.github/workflows` (with ShellCheck on each step's script) and hadolint on the `Dockerfile` (`.hadolint.yaml`), each at its version in `tools.toml`, as callboard and GitHub run them. |
| `callboard/coverage.py` | **Coverage**: how much of the code the tests reach, held by how settled it is (`git blame`): each fresh function and route reached by a test, settled code at 98%, and the release bar (98% overall, every file 90%). Through `checks.py`; no installs needed. |
| `callboard/policy.py`, `plan.py`, `board.py`, `gate.py`, `notes.py` | The rules (`callboard.toml`, read for every tool), the plan of a run, the board that draws it, the gates, and the change notes and manual release items the Gates page and `release.py` share. |

The loop is: edit on your computer → `callboard push local` → refresh `http://<nas-ip>:8643`. Nothing reaches GitHub (or the real app) until you commit and push.

## What callboard does

```
callboard [<code>]         check that code: the tests and checks, and how the NAS stands beside it (in sync, or how
                          many files are out). Nothing is copied; p on the board pushes it while the checks run
callboard push <code>      push it: copy it to the NAS and restart the app (always, files to copy or not), the checks alongside
callboard restart          restart the app, copying nothing
callboard status [<code>]  how the NAS stands beside that code, as JSON (what the UI's Connected to shows)
callboard init             set up callboard for a project (a .callboard's old check settings moved to callboard.toml)
callboard gate <name>      the checks as that gate holds them (push, merge, release), the same as GitHub runs
callboard hook install     a pre-push hook that runs the push gate (callboard hook remove takes it out)
callboard config show      every integration's rules as they stand for this code (callboard config show)
callboard ui               the callboard UI: the last run in your browser, a fresh scan of the checks, Push and Restart

<code> (local when it's left out):
  local      your folder as it is now (uncommitted changes included)
  master     the latest code on GitHub's default branch (main or master)
  dev        the latest code on GitHub's dev branch
  release    the newest release tag, e.g. v1.2.0
  beta       the newest tag including pre-releases, e.g. v1.3.0-beta.1

  -n  dry run: list what a push would copy and run the checks, change nothing
  --tests-first  push nothing until the checks have passed (with push, or p on the board)
  --skip-tests   don't run the tests and checks
  --skip-future  run the current tests only, not the future ones
  --gate <name>  the checks as that gate runs them (push, merge, release: callboard.toml's [gates]), in diff mode
                 where the gate says so: only what changed since the gate's base
  --diff         diff mode on its own: only what changed since the branch's upstream
  --no-sample    Wardrobe only checks: no sample of the looks waiting is made (r makes it first then)
  --checks-only  the checks alone, nothing copied (what the UI's "Run the checks again" runs)
  --only <id>    one block alone, by its id in callboard.toml: unit, future, dhtml, types, build, coverage, audit, i18n,
                 release, upkeep, style…
  --sync-only    with push: the push alone, no checks (the UI's Push)
```

Everything runs **at the same time**, each step in a section of its own on a board about half a screen tall (`callboard/board.py`), redrawn as it goes: a block that's blue while the step is under way, then green (passed), orange (a warning: stopped with Enter, dependencies behind or CVEs to act on), red (failed) or grey (for the record: skipped, not run, already in sync): a header, its progress bar (the one it moved last) (`callboard/progress.py`'s, the same bar each tool draws on its own, sent to the board: `PLEXCACHE_PROGRESS=feed`) and the last line it printed. 

On top, the board's header: what's checked (`Local Copy on Dev`; `Committed Copy on Main` or `on Dev` for `master`/`main` and `dev`, `Release Copy of v1.2.0`, `Beta Copy of v1.3.0-beta.1`), the code's role or phase (`· development`, `· release`, `· freeze (v1.2.0-rc.1)`: what its checks are held to, below), the run's modes (`· push gate`, `· Diff`, `· Tests first`, `· Dry run`), the commit (`a1b2c3d`, `+ uncommitted` when your folder has changes; the first thing cut on a narrow terminal) and the time since the board started, which stops when the last block ends. Under it, the keys (`[Enter] Cancel`, `[u] Open the callboard UI`, and `[r] Review Style Changes` while the style review is offered) and, on the right, how many blocks are done (`6/8 done · 1 failed`, the failed and warnings only when there are). One letter of each block's title is underlined while the board runs: pressing it opens that block's page in the callboard UI (below).

Every block reads the same way: its title, its status in capitals and its time; its bar (`done/total` and the item under way or what it did, with how many workers do it on the right, under the time); and one result line (`callboard/progress.py`'s `result`: facts joined with ` · `, no time, no workers and no count the bar already shows, so a passing suite's says what it ran on — `Python 3.15.2 · Node 26.12.0 · …`, a nightly's build stamp left off — and a failing one `3 failed · …`).

**What's on the board, and what each block is held to, is the project's `callboard.toml`** (at the root, committed; `callboard/policy.py` reads it, and `callboard config check` says whether it's well formed). Its `[integrations]` table lists each block in the order it's shown — its title, its kind (which tool's rules it follows: `tests`, `checks`, `coverage`, `audit`, `i18n`, `release`, `upkeep`, `style`), the command that runs it, the blocks it waits for (`after`) and the files it needs (`needs`) — and one that's switched off (`enabled = false`) or not set up (no command, or a file it needs missing) is hidden everywhere but the UI's Integrations page. The letter that opens each block's page follows the menu: the first free letter of its title, Hub and Sync first (so `h` is the hub, `s` the sync, `u` the unit tests, `f` the future tests, `d` DHTML, `v` the Python validation, `b` the build, `c` coverage, `e` the security audit, `t` translations, `l` the release checks, `n` dependencies, `y` style approval; `p`, `a` and `r` are the board's own), unless the integration asks for one (`letter = "x"`).

Under each integration's id are **its rules**: what each thing it finds is — a failure (`"fail"`: red, the run fails), a warning (`"warn"`: orange, said but nothing stopped), only told (`"info"`: grey) or ignored (`"off"`) — and its numbers (a threshold such as `settled = 98`, a window such as `fresh_days = 14`, with its own level when it isn't the integration's: `every_line = { value = 98, level = "fail" }`). The rules differ by the **role** the code has: its branch's (`[branches]`: `main` and `master` release, `dev` develops, `hotfix/*` is a hotfix, anything else a feature; `preset` names a common layout) or, once a version tag is on it, its **phase** (`[tags]` and `[phases]`: a `vX.Y.Z-beta.N` tag puts the code in its preview, the release's rules as warnings; a `vX.Y.Z-rc.N` in its freeze, the release's rules as they are). `[<id>]` holds an integration's **default** rules, the ones every role starts from, `[<id>.<role>]` what differs for one (over what the role inherits, `[roles]`: a hotfix inherits the release's rules, a feature the development's), `[<id>.diff]` what differs in **diff mode** (a gate that looks only at what changed since its base; a rule marked full-only is skipped then, and said so). So a run on `dev` can't fail on what only a release needs (the release checks and the translations only tell there), and the same code on `main`, or tagged as a release candidate, is held to the release's rules — the role is worked out once, by callboard, from the code being checked (`CALLBOARD_ROLE` and the rest of the context in each block's environment), so a copy of main is held to main's rules wherever it's checked, and the board, the UI, the tools run by hand and GitHub can't disagree. No tool decides a level or a number itself: each holds only a schema of its settings, and reads the file. A rule not set is off. `callboard config show` prints every integration's rules as they stand for the code; the UI's Config tabs show and save them (below). `callboard/starter.toml` is what `callboard init` writes for a new project: these rules, as they were before the file. **A rule is never loosened to make a check pass** (`CLAUDE.md`): the code is fixed, or the maintainer asked.

A check says what it found and exits by the worst of it: 0 passed, 1 a failure, 2 it couldn't run, 3 only telling (grey, `IN PROGRESS`), 4 a warning (orange), 5 not set up — the same for every block (`callboard/checks.py`, which every check tool goes through; its note beside the block's title is the tool's).

1. **Sync to the NAS** — on a push, copies only what changed with rsync over SSH (a bar of the files as they go), and deletes files on the NAS that you deleted locally. Installed packages (`node_modules`, from `npm ci`) never go: the NAS runs the source as it is. It then **restarts the test app** with TrueNAS's own `midclt call app.redeploy plex-cache-dev`, and waits until TrueNAS says it's done: you can refresh the page and try your change while the checks run. A push always restarts, even with nothing to copy: the app reads its pages and scripts from disk as they're asked for, but its Python only when it starts, so a copy without a restart leaves it running half old code (a new page, yesterday's `/theme.js`). On a check (`callboard local`), the block only says how the NAS stands — `already in sync`, or `out of sync: 12 files to push · 9 changed · 2 new · 1 to delete` — and `[p] Push and restart` on the board's header pushes this code there and then, the block running the push while the checks go on (with `--tests-first`, once they've passed). When a push's restart failed, a check says the app hasn't been restarted since the copy, and p (or the next push) restarts it.
2. **Unit Tests** (`unit`: `python3 tests/run.py --coverage --exclude WebBuildTests --exclude StyleGuideTests`; its rules `failures`, `warnings`, `skipped` — a warning the run printed only tells on dev, fails at release: `--coverage` saves what of the code they ran, every worker's, for the Coverage block), on exactly the code it copies (for `master`, `dev` and the rest, a copy from git, with your folder's installed packages linked in for the web tests; it installs those itself first, `npm ci --prefix dev`, when they're missing or `dev/package-lock.json` has changed).
3. **Future Tests** (`future`: `python3 dev/future.py --exclude StyleGuideTests`; off at release, never a release's concern: the same suite on the next Python, see below: a bar for the image build, then one for the tests), stopped as soon as a unit test fails (`stop_with = ["unit"]`; the unit tests run on to their end, so every failure is still listed). `--skip-future` leaves them out when you're in a hurry.
4. **DHTML** (`dhtml`: `python3 tests/run.py tests.test_plexcache.WebBuildTests`: `WebBuildTests`, Stylelint, ESLint, TypeScript, html-validate, axe-core and the build), the web's checks from the suite, in a section of their own.
5. **Python Validation** (`types`: `callboard tool typecheck`, as GitHub runs it; its bar the files checked): pyright's type check (`pyrightconfig.json`, `--warnings`: its standard rules, on the app, the dev tools and the tests, a type-ignore that no longer does anything included) and Ruff's lint (`ruff.toml`: unused imports and variables, likely bugs, older syntax Python 3.15 says more simply, the import order, the security rules), at once, each at its version in `dev/tools.toml`, through the check tools' shared code (`callboard/checks.py`). Its result line says what each found (`0 errors · 0 warnings · 0 Ruff findings`). Ruff is installed the first time, at its pin, into `~/.cache/plex-cache/tools/ruff-<version>` (nothing goes into your Python); `callboard tool typecheck --fix` makes Ruff's safe fixes (the import order, unused imports) in your folder, then checks. A rule that's wrong for a line is said so there (`# noqa: <code> — why`).
6. **Build Validation** (`build`: `callboard tool buildcheck`, as GitHub runs it; its bar the files checked): what builds and ships the app — ShellCheck on any shell script the project has (callboard's own script is checked in its project now), actionlint on the workflows (with ShellCheck on each step's script), hadolint on the `Dockerfile` — at once, each at its version in `dev/tools.toml`, fetched the first time into `~/.cache/plex-cache/tools/` (checked against the checksum there). Every finding counts, notes and style too, kept at zero: a rule wrong for a line says so there (`# shellcheck disable=SC… # (why)`), and a rule is only turned off in `.hadolint.yaml` with the maintainer's say, its reason beside it (DL3008, pinning apt packages: the image takes Debian's newest patches on purpose).
7. **Coverage** (`coverage`: `callboard tool coverage --callboard`), once the unit tests have passed, from what they saved (nothing is run again): green when every rule is met, orange with what's missing — a warning on dev, like the looks to approve: it neither stops the copy nor fails the run. At release (`[coverage.release]`), the bars of the whole codebase (`every_line`, `each_file`) are a check like the others: red when they aren't met. See **Coverage** below.
8. **Security Audit** (`audit`: `python3 dev/audit.py`, when `dev/audit.toml` is there — `needs`): which app code no security audit has seen, from each audit's record and git — green when every rule is met, orange when unaudited code is past its grace window (or sensitive code waits at all) — a warning, like the looks to approve, that neither stops the copy nor fails the run. At release (the code tagged a release candidate, or on main) its release rules are a check like the others: red; a rule that needs the private audits repo where there isn't one is said (`unknown`), never passed quietly. It reads the records, not the tests, so it starts straight away. See **Security audits** below.
9. **Translations** (`i18n`: `python3 dev/i18n.py --callboard`): how far the translation catalogs are, overall — one number across every language (`32.9% translated · 15 languages · 3552 texts`). Each language is a unit of its own, so its bar counts the languages at their target (`0/15 languages at target`); a language whose target here is 0% isn't met until it's complete, said in grey (`32.5% translated, no target here`), never failed. On the Config tab each language's target is a row of its own: every language (`*`), then each one you add with **+ Add a language…**, and the level for one short of it. Its rule is a target per language (`targets = { "*" = 0 }`: a code, a group, or `"*"` for every language, each the share of the texts translated): between releases the catalogs may lag, so the target is 0 and the block only tells, grey, `IN PROGRESS`; at release (`[i18n.release]`: `{ "*" = 100 }`, `unused = "fail"`) every text must be translated and no catalog entry unused — anything missing is listed per catalog and the block is a failure, red, like a failing test; a preview (a beta tag) says the same as warnings. In diff mode, `present` asks that each text added since the base is in every catalog. See **Translations** below.
10. **Release checks** (`release`: `python3 dev/release.py --callboard`), every run, as an overall readiness: everything that has to be true of a release, each its own line and its own rule (`version`, `translations`, `mqtt_settings`, `mqtt_docs`, `coverage`, `audits`, `looks`, `change_notes`, `manual`) — the version a new `X.Y.0` above what `main` and the release tags have, every translation catalog complete, every setting placed for MQTT (a control in Home Assistant, or listed in `NOT_OVER_MQTT` in `plexcache/homeassistant.py` with why it isn't one), the README's MQTT topics and commands the ones the code has, the coverage release bars met (from what the tests saved), the security audits' release rules, every look approved into the style guide, at least one **change note** written since the last release (a file under `changes/`, `notes_dir`: one per change, written as the work goes; the GitHub Release's notes are made of them, `python3 dev/release.py notes`), and every **manual item** ticked for the version (`manual_items`: what a person does for a release, ticked on the UI's Gates page or with `python3 dev/release.py tick <item>`; the ticks are kept under `changes/`, to commit). Each requirement is a unit of its own, so its bar counts them: `3/9 requirements met`, a miss held as fail counted red, as warn orange, as info neither (the bar's grey rest). Between releases it only tells: grey, its line the readiness (`4 of 9 ready · to go: version, translations, coverage`). At release — the code on `main`, or tagged a release candidate (`python3 dev/release.py candidate`) — every rule is `"fail"`: red when it fails, what it found printed above the board, and with `--tests-first` nothing is copied; a preview (`python3 dev/release.py start`: a beta tag) says the same as warnings. `callboard release` is something else: the newest release tag synced.
11. **Dependencies** (below).
12. **Wardrobe**, the style review (`style`: `python3 dev/style.py check`; `waiting = "warn"`: the looks waiting for your approval, see "The style guide" below), on its own: green when every look is approved, orange when some wait, its block saying how many and the command to approve them (`python3 dev/style.py review`, which makes the sample again first when the page is out of date). When looks wait, the block then makes their sample there and then (`python3 dev/style.py sample`, its bar on the block: `LOOKS WAITING: MAKING SAMPLE`; the pages photographed several at once, its workers beside the bar), in your folder, so the review opens at once; one that can't be made leaves the block `LOOKS WAITING: NO SAMPLE`, what it said above the board, never a failure. Only one sample is made at a time: a review or sample started meanwhile waits for it. `--no-sample` leaves it to the check alone, as it was: no sample, no review at the end. Once it's made, the header offers **r**, and the review page opens in your browser. And once every other block is done (none failed, on a terminal, not a dry run) with looks still waiting, the review is the block's last step on the board: blue `IN REVIEW`, the page's address its line, the board kept up until you close the page (Enter skips it: `LOOKS WAITING` again); then the check again, and the block ends green `ALL APPROVED` (`6 approved just now · commit dev/style-guide.json`) or yellow with what's left. Once they're done, the block says the command instead. Nothing it found is printed above the board; it doesn't hold up the copy (`--tests-first` included) or the future tests, and its warning isn't a failure. It's the last block on the board, and runs every time, even on code that already passed, since it's quick.

Each section keeps the same three lines from the start, its whole block in its colour, so nothing moves as it fills in; when a step ends, its result is in its own block, and nothing is said again after it. What a failed step printed (the tests' failures in full), and the dependencies' box when they aren't all current, go *above* the board as the step ends, so the board stays put at the bottom of the screen: scroll up to read them. Enter stops the checks (a copy under way finishes). The test app is already running that code (unless `--tests-first`), so fix it and sync again.

The **dependencies** (`upkeep`: `python3 dev/upkeep.py --callboard`; `behind` and `cves` warnings, the CVE windows in days, and `move`: which releases it moves itself in this checkout — `"all"` on dev, `"minor"` on main, `"none"` elsewhere) are looked up in your folder rather than the copy while the rest runs; once the checks are done it runs again (from the day's answers) to move what it moves, so a pin never changes under the tests, and shows one last box: green when everything is at upstream's newest release; yellow with each package that has a new version and what to do about it (a major release is yours to move; a minor or patch one moves by itself on `dev`); grey when upstream couldn't be reached. With `dev` checked out, the minor and patch releases are moved there and then, in your folder: the box lists them, to test (the next `callboard`) and commit. With `main` checked out, only minor and patch releases count: they're moved there the same way, and a major release isn't reported at all (majors are only ever taken on `dev`, and reach `main` when dev is released). On any other branch it only reports.

**If the NAS already has exactly these files** (compared by content, so the same code from another branch counts too), nothing is copied and the app isn't restarted. If the last tests callboard ran on that code passed, the Sync block says it's already in sync and each check's block that it already passed (grey), and nothing runs but the dependencies. If they failed (or there's no result yet, `callboard.toml` changed, the last tests weren't run for this code's role or phase — a pass as dev doesn't count for the same code as a release candidate: its rules differ — or the last run was a different command such as `callboard master`), the Sync block says the files are in sync (grey) and the checks run again. The last result is kept in `~/.local/state/callboard/`.

With `--tests-first`, the copy waits for the checks, and if any fail (from the first failing test, not once the suite ends) **nothing is copied and the app isn't restarted**, so the NAS keeps running the last good code. Use it when the test app needs to stay working (for example, before syncing `master` or a release).

`master`, `dev`, `release` and `beta` copy exactly what's in git at that point; they never touch your working folder.

callboard isn't specific to this project — any project with a `callboard.toml` (and, to push, a `.callboard`) in its root can use it: `callboard init` writes both.

**The gates.** A gate is a run of the checks at a moment, as `callboard.toml`'s `[gates]` holds it: **push** (the pre-push hook `callboard hook install` puts in, and a push on GitHub), **merge** (a pull request) and **release** (a release tag). Each says its mode — `diff = true` looks only at what changed since the gate's base (push: what the upstream hasn't; merge: the branch merged into; release: the last release tag) — and whether GitHub runs it: `github = true` a required check, `"warn"` reported but never blocking, `false` skipped (a skipped required check counts as passed, so a gate switched off blocks nothing); `[github] enabled = false` keeps GitHub out of all of them until you say. `callboard gate push` runs one here exactly as GitHub would (`callboard/gate.py`: the same plan, the same tools, a record like any run); `.github/workflows/gates.yml` runs the gate each event is (a push, a pull request, a tag), and `.github/workflows/publish.yml` the release: a version tag pushed runs the release gate, builds and publishes the image at that version, makes the GitHub Release (its notes the change notes since the last release; a beta or release candidate a pre-release), and after a release proper opens a pull request moving `__version__` on to the next `X.Y.0` (`python3 dev/release.py bump`). A release is started with a tag, not a flag: `python3 dev/release.py start` tags the next beta (the code in its preview phase from then on: the release's rules as warnings), `candidate` the next release candidate (its freeze: the release's rules as they are), `hotfix <name>` makes a `hotfix/<name>` branch off the release branch, and `git push origin <tag>` sets GitHub going.

**Every run leaves a record** in `~/.local/state/callboard/runs/<when>-<n>/`: the plan callboard wrote (`plan.json`: what the run is and each block's command), each block's output (`logs/`), the board's state as it went (`state.json`, rewritten as each block moves), each block's result (`results`) and each tool's detail for its page (`detail/<block>.json`). The newest 30 are kept (`CALLBOARD_KEEP_RUNS`). The UI reads them; nothing else does.

(callboard was called tnsync: a project's `.tnsync`, `~/.config/tnsync/config` and the state it kept in `~/.local/state/tnsync/` are still read — the state folder moved over once — but `.callboard` and `~/.config/callboard/config` are their names now, as are the `CALLBOARD_*` variables and the tools' `--callboard` flag.)

## The callboard UI

`callboard ui` (or `u` on a running board) opens the board in your browser: a **hub** with a card per block — its colour, its bar, its result line, when it last ran — and, when nothing is under way, starts a fresh scan of the checks (`--checks-only`, as the last run was: its code) whose numbers fill in as they come. It shows the run as it was last time until then, so there's always something to look at. The page follows the app's themes (Classic and Dionysus, light and dark: the pickers in its sidebar) with the app's own stylesheet; its own looks (`callboard/devui.css`) are outside the style guide, so no approval is asked for them.

Behind each block is a **page** of what its tool found, opened by its letter (on the board, in the sidebar, or typed on the page: the letters follow the menu, above — `h` the hub, `s` Sync, `u` Unit Tests, `f` Future Tests, `d` DHTML, `v` Python Validation, `b` Build Validation, `c` Coverage, `e` Security Audit, `t` Translations, `l` Release checks, `n` Dependencies, `w` Wardrobe; the audits and the style review keep their own pages, `a` and `r`). Each page has the block's bar, its result last time, its tool's detail, the board's Issues for it, its output, and **Run again** (`--only <block>`: that block alone). The detail is the tool's own account, written by the tool as JSON beside the record (`callboard/progress.py`'s `detail`, in the file the board names with `CALLBOARD_DETAIL`): the page only shows it, so the board, the UI and the tool can't disagree about what happened (one source of truth: the tool).

| Page | What its tool writes |
|------|----------------------|
| Unit Tests, Future Tests | `tests/run.py`: the counts, each failure as unittest printed it (with the command to run it alone), what it ran on, the slowest classes. The Future page adds the channels' picks (each dependency's pre-release or stable), the image build and each part's result. |
| DHTML, Python and Build Validation | `callboard/checks.py`: each tool, its version, what it found (`file:line:col`, the rule, fixable or not) and the files it read. |
| Coverage | `callboard/coverage.py`: the totals, the rules, each fresh function and whether a test reaches it, each file's cover and the lines not run, then the checks' findings. |
| Translations | `dev/i18n.py`: how far each language is, what's wrong in each catalog, the English in `app.js` that doesn't go through `T()`, and **Export** per language: the file `python3 dev/i18n.py missing <code>` prints (translate the values, then `merge`). The page is read-only: the catalogs change by `sync` and `merge` only. |
| Release checks | `dev/release.py`: each check as it came, its level for this role, what to do for one that isn't met, how many are ready, the rules skipped in diff mode. |
| Dependencies | `dev/upkeep.py`: each dependency pinned and newest, what moved here, what's new upstream and whose it is to move, the CVEs as judged, the box as the board shows it. |
| Sync | the push: what went where, each file rsync listed, whether the app was restarted. |

The hub's buttons run callboard itself, one at a time, in the project: **Run the checks again** (`--checks-only`). Its **Connected to** card says where callboard pushes — the app, the NAS and its folder, and the Dionysus that answers at the app's web port (`TN_WEB_PORT` in `.callboard`, 8642 if not set): its fingerprint and identicon, as its own pages show them, from its open hello — and how the NAS stands beside the code picked there (Local, Dev, Master, Release, Beta: `callboard status <code>`): in sync, or how many files are out (changed, new, to delete), with the last push and restart. **Push** pushes the code picked (`callboard push <code> --sync-only`: copied and restarted, nothing else) and **Restart** restarts the app (`callboard restart`); beside them, a tally of how the checks stand (failed, warnings, passed, and what's still to go). The run they start writes a record like any other, and the page follows it; the card asks the NAS again once it ends (or on refresh). The hub's sub-line says the code's role or phase, the gate and the mode, as the run had them.

Its **Integrations** page lists every integration `callboard.toml` names, on the board or hidden (off, or not set up), with its letter, kind, command and what it waits for; each has a **Config** tab: the integration's rules as the file holds them — the default table, then a tab for each role it sets something for (another is added from **Add a role**, and a role's tab can be removed), and each one's **Diff Checks** behind an arrow (open when it has some), every setting a field by its kind (a level, a number with its own level, a toggle, a list, targets) with what it decides beside it — and, under them, the rules as each role reads them once its inheritance and cap are applied (what `callboard config show` prints). **Save** writes `callboard.toml` again (the whole file, checked against the schemas first; comments aren't kept) and commits nothing: the change is in your folder, to look at and commit like any other; `[config] read_only = true` keeps the tab to showing. The **Gates** page says what each gate is and what GitHub runs of it, the tags and phases, the branches' roles, the change notes written since the last release, and the manual release items, each ticked there once it's done. Its **Runs** page lists the records.

The page is served to this computer only, to the browser that opened the printed address only (`callboard/devpage.py`), and the UI closes when the page is: `callboard ui --no-browser` prints the address instead of opening it, `--no-scan` skips the fresh scan, `--port <n>` picks the port.

## Setting it up (once)

### 1. On TrueNAS

1. **SSH:** System → Services → SSH: turn it on (and tick "Start automatically").
2. **Your key:** Credentials → Users → `truenas_admin` → Edit → paste your computer's public key (`cat ~/.ssh/id_ed25519.pub`; make one with `ssh-keygen -t ed25519` if you don't have it) into **Authorized Keys**. Check it works: `ssh truenas_admin@<nas-ip>`.
3. **Permission to restart apps:** on the same user, add `/usr/bin/midclt` to **Allowed sudo commands with no password**. (callboard tries `midclt` directly first and falls back to `sudo -n midclt`.)
4. **Folders for the test app** — in the TrueNAS shell (change the paths if your apps live elsewhere):
   ```sh
   sudo mkdir -p /mnt/ssd/AppConfigs/plex-cache-dev/src /mnt/ssd/AppConfigs/plex-cache-dev/config
   sudo chown truenas_admin /mnt/ssd/AppConfigs/plex-cache-dev/src
   sudo chown 568:568 /mnt/ssd/AppConfigs/plex-cache-dev/config
   ```

### 2. On your computer

1. **Get callboard and put it on your PATH** (the tests and this folder's tools need it too: they're built on it):
   ```sh
   git clone https://github.com/drsassafras/callboard ~/Code/callboard   # (beside this project; once for every project)
   chmod +x ~/Code/callboard/bin/callboard
   mkdir -p ~/bin
   ln -sf ~/Code/callboard/bin/callboard ~/bin/callboard   # ~/bin must be on your PATH
   ```
   (If `callboard` then says "permission denied", the `chmod +x` was missed.)
2. **Your NAS's address**, shared by every project — `~/.config/callboard/config`:
   ```
   TN_HOST=192.168.1.10
   TN_USER=truenas_admin
   TN_PORT=22
   ```
3. **This computer's settings for the project** — `.callboard` in the project root (it's in `.gitignore`, so each person keeps their own): where the test app is, and what's copied.
   ```
   TN_APP=plex-cache-dev
   TN_DEST=/mnt/ssd/AppConfigs/plex-cache-dev/src
   TN_PATHS=plexcache
   TN_EXCLUDE=.git .DS_Store __pycache__ *.pyc
   TN_WEB_PORT=8643
   ```
   `callboard init` asks for these and writes both files for you. Settings are read as `KEY=value` lines, never run. The checks themselves — which run, with what command, held to what — are the project's, in `callboard.toml` (committed; `callboard init` writes `callboard/starter.toml` when there's none). An old `.callboard`'s `TN_TEST`, `TN_VALIDATE`… lines are taken out by the first run that meets them, kept in `.callboard.before-toml` (not committed either). Nothing in `.callboard` is run as a command.

### 3. The test app

1. Run `callboard push local` once **before** installing the test app (its restart fails then: the app isn't there yet), so its code folder exists (otherwise Docker creates an empty one and the app won't start).
2. Open `compose.dev.yaml`, make the media lines match your real `plex-cache` app (and Plex), and set your NAS's IP in `x-portals`.
3. TrueNAS: Apps → Discover Apps → ⋮ → **Install via YAML**, name it `plex-cache-dev`, paste the file.

After that, `callboard push local` is all you need (or `callboard local`, and p on the board when you want it on the NAS).

## The CSS, the scripts and the pages

`plexcache/web`'s CSS, scripts and pages are written as they're read, checked against one floor of target browsers and built for the image by `dev/web.js`. The floor is an age: every browser version out in the last five years (`"browserslist"` in `dev/package.json`, `last 5 years`; in November 2026 that's Safari and iOS 15.2, Chrome and Edge 96, Firefox 95 — about 97% of use). One age holds every browser to the same date, so the CSS, the scripts and the HTML can't disagree on what's supported, and the window moves on by itself: each build is checked against the browsers of its own day, so what an old browser lacks stops counting once it falls out of the window, and the pages may then use it. QQ Browser is left out (caniuse's data for it: an old engine without `min()`).

- **The CSS** is written **without browser prefixes** (`-webkit-`, `-moz-`, `-ms-`, `-o-`): write the standard property and leave the prefixes to Autoprefixer. It may use newer standard CSS that **postcss-preset-env** rewrites for the targets (nesting, the media range syntax `(width >= 600px)`, `lab()` and `oklch()` colours and the rest of its stage 2 features): the build writes them out as CSS the oldest targets read, keeping the newer form beside it where the plugin does. What it can't rewrite (container queries, subgrid, `:has()`) is held to the floor as before. Only `app.css` is built: the pages' and scripts' own styles and the themes' CSS reach the browser as written, so they keep to CSS the targets read. An old Safari throws out a whole rule when one of its selectors is new to it, so a newer selector (`:focus-visible`, `:has()`) gets a rule of its own rather than sharing one (`.x:hover{…}.x:focus-visible{…}`, not `.x:hover,.x:focus-visible{…}`); cssnano, told the targets, keeps them apart.
- **The checks**: Stylelint on the CSS, ESLint on the scripts and html-validate on the pages and on every page as the app draws it — each with its recommended checks (html-validate's `standard`), none turned off — and each with a check that nothing it uses is missing from a target: stylelint-no-unsupported-browser-features (caniuse's data), eslint-plugin-compat, and for the HTML a check of every element, attribute and input type against MDN's data (`dev/web.js`). The CSS is checked twice: as written (Stylelint's checks, no prefixes), and as the oldest targets get it — what postcss-preset-env makes of it, the newer forms left out — for what a target lacks, each finding told by the line it's written on. So a feature the build rewrites passes, and one it can't is found. A finding is fixed in the code.
- **The scripts' types**: TypeScript checks the app's own scripts together, as they are (checkJs, not strict: `dev/jsconfig.json`), for a property that isn't there, a call with arguments nothing takes, or a value of the wrong kind. What it can't see from the code is written down in `dev/web.d.ts`: the page's globals, the element a handler's event comes from (`/** @param {On<MouseEvent>} e */`), and a card's rows (`Row`). Its ESLint rules beside the recommended ones: `no-var`, `prefer-const`, `no-shadow`, `eqeqeq` (smart: `== null` stays), `no-implicit-globals` and `no-unused-vars`.
- **Accessibility**: axe-core's standard rules, none turned off, on every page of the app as the two demos draw it (`tests/demo.py`: the showcase and the one with problems), in Classic and Dionysus, light and dark (`node dev/web.js a11y`, about two minutes). Each finding names the element, the rule, and the pages and looks it's on. A colour that fails its contrast is a look: its fix is shown in the style sample and waits for the maintainer's approval like any other. Chromium is Playwright's, at `dev/package.json`'s version (`npx --prefix dev playwright install chromium`, once), or the one `PLEXCACHE_CHROMIUM` names.
- **What the pages can do without** (`"graceful"` in `dev/package.json`): the few features a target lacks that only do nothing there — a focus ring an old Safari draws its own way, a cursor on a phone, `loading="lazy"` on posters — each named with why. The checks pass over these only; a new one is a choice, and `WebBuildTests` lists them. When the window has passed one (the checks no longer find it with the entry taken out), it comes out.

The image build (the Dockerfile's `web` stage, on Node's LTS) runs `dev/web.js build` on each: the CSS gets its newer features rewritten for its targets and the prefixes they still need and is minified with cssnano, the scripts are minified with Terser and the pages with html-minifier-terser; those copies replace the source's in the image. `callboard` copies the source as it is, so the test app serves it unprefixed and unminified — fine for a current browser.

```sh
node dev/web.js lint                         # Stylelint, ESLint, TypeScript and html-validate on plexcache/web
node dev/web.js a11y                         # axe-core on every page, both demos, each look (once: npx --prefix dev playwright install chromium)
node dev/web.js build plexcache/web/app.css  # what the image ships, to stdout (--no-minify: prefixed only); a .js or .html the same
```

The suite checks it (`WebBuildTests`): no prefix written by hand in the CSS, the pages' and scripts' own styles or the themes' CSS; every check clean on every stylesheet, script and page, on the server's `/theme.js` and on every page as drawn before and after the first checks; the floor and the graceful list as they're meant to be; no newer selector sharing a rule; the CSS build clean, only adding prefixes and fallbacks (every declaration written kept, in order); the CSS check passing what postcss-preset-env rewrites and finding, by its line, what it can't; the built scripts drawing every page as the source does, and the built pages keeping every tag and word. They need `npm ci --prefix dev` (GitHub's test job runs it); without node they skip, like the page tests.

## The style guide

Every look the app wears is one the maintainer approved, and `dev/style-guide.json` lists them all: each rule of `plexcache/web/app.css` (by its selector and media query, with its declarations), each `style="..."` a page or script writes, each style property a script sets, each drawing (an icon, the grape arrow, a chart's marks), what `plexcache/web/decor.js` draws (run on a fixed page by `dev/decor-draws.js`, so a change to its code that draws the same needs no approval), each part of the themes' CSS (`themes.py`'s `css()` and `script()`), every colour, font and decoration of the built-in themes, and every image and font the app ships. `StyleGuideTests` fails on any look that isn't in the guide, isn't as the guide has it, or has gone from the code, and on a guide edited by hand (its seal won't match).

A new or changed look goes in only like this:

```sh
python3 dev/style.py check     # what differs from the guide
python3 dev/style.py sample    # optional: makes the page ahead (each of those Before and After, side by side); review does it when needed
python3 dev/style.py review    # the maintainer, at a terminal: the page with Approve all and an Approve per change
python3 dev/style.py approve   # the same at a terminal without the page: type "approve" to add them all
```

`sample` needs Playwright, like the screenshots (`npm ci --prefix dev && npx --prefix dev playwright install chromium`); it shows the dev tools' progress bar while it works. It starts two demos with the same data, today's app and the app as approved (today's with the approved look files put back: the files `approve` keeps in git, their blob ids the guide's `files`, so the Before is the app's own history and never a copy nobody can read in a diff; or a folder given with `sample --before <folder>`), photographs each look on both in Classic and Dionysus, light and dark, cropped to the same spot, and compares them pixel for pixel. The page shows only what looks different, Before and After side by side (with a button that marks the pixels that changed); a look drawn on no demo page as its code, Before and After; and, folded away, the looks whose code changed but that drew exactly the same, which need no looking at (approving still covers them). A look seen on whole pages (a theme's colour, a shipped image) is judged against its own file put back alone, so another change on the page isn't taken for it; `decor.js` can't run with another day's styles, so its looks are judged against the whole Before. When the Before itself isn't exactly as the guide has it, the page says which looks. Words aren't a look: what the app says is content, so rewording a title, a label or a tooltip needs no approval (in a look, any text with a letter in it is `…`: between tags, in the attributes people read, in a stylesheet's `content`), and the Before takes today's pages, scripts and translations for a stylesheet's rules and the whole-page looks, so a reworded title doesn't show as a difference either. Each pair has "Highlight the difference" and a slider view (full width: click or drag on the picture, or the slider under it, to move between Before and After). `review` serves that page to this computer only (127.0.0.1), and to the browser that opened the address it printed only (a one-time code swapped for a cookie, `callboard/devpage.py`; with a token the page's buttons send) while it runs, and only when started at a terminal: "Approve all", or "Approve" on one change, puts those looks in the guide (each only if it still differs exactly as the sample showed it), and an approved change leaves the page; it closes once everything is approved, or after an hour unused (`review --board` is callboard's r: what it says goes to `dev/style-sample/review.log`); once everything is approved it keeps the approved files in git too. `check` fails with how many looks wait and, on callboard's board, a line linking the page (or saying it's out of date). `approve` only takes a sample of exactly the looks that differ now (its fingerprint; change the code after and it asks for a new sample), keeps the sample's fingerprint and the date in the guide, keeps the approved look files in git (`git hash-object -w`, their ids in the guide's `files`: the next sample's Before; commit the files as they were approved, with the guide), and won't run without a terminal. Nobody but the maintainer approves, edits the guide or loosens the test (`CLAUDE.md`). A theme someone uploads on System → Themes is their own: the guide covers the code.

## Security audits

Security audits are done by people, and `dev/audit.py` keeps track of what each one saw, line by line, so nothing is forgotten and you can see where auditing is thin. An AI auditor can do one too, when one is installed on your computer (below).

**Each audit has two halves** with the same id (`2026-11-10-1`: the day and a count, never who did it):

- **public**, here in `security/audits/<id>.toml`: the day, the dev commit audited, `full` or `partial`, and a partial's scope (whole files, or whole functions as `path:function`);
- **private**, in the private audits repo (checked out beside this one, `~/Code/TrueNAS-Plex-Caching-audits`; `private` in `dev/audit.toml`, or `PLEXCACHE_AUDITS`): the **auditor** (a person as `human:name`, or an AI auditor's id), its **thoroughness** (1 the most thorough … 5: for a person, how closely they read it, 1 every line traced, 2 line by line, 3 read closely, 4 read through, 5 skimmed; for an AI auditor, its effort), and its findings. Its `rules.toml` holds the release rules, since they name auditors; its `FORMAT.md` every field.

**A line counts as seen** by an audit when it's in the audit's scope and hasn't changed since the audit's commit: `git blame` says which commit last changed it, and that commit is the audit's or one before it. So a line goes stale by itself when it changes; nobody marks anything. Each record also carries the **fingerprints** of the lines its audit read (`prints`, written by `record`): a short hash of the path, the line and its neighbours. A line whose fingerprint an audit has counts as seen by it too, so you can audit code before you commit it (`commit` is the one you're on, and the record says `uncommitted = true`): once committed, in one commit or several, squashed or rebased, it stays seen, until it or a line next to it changes. The block also says how many unaudited lines aren't pushed yet (uncommitted, or ahead of the branch's upstream), so you can audit them first. `dev/audit.toml` says what counts as app code (`plexcache/`, the web's scripts, pages and CSS, the `Dockerfile`, `compose.yaml`, the workflows, `callboard`, and the dev tools that serve a page on this computer or run commands on it: the audits page, its runner and AI auditor plugins, the style review, the board; not the tests, translations, docs or the other dev tools).

**The rules:**

- on dev (from `dev/audit.toml`, any auditor): code no audit has seen waits no longer than `grace_days` (7), nor adds up to more than `grace_share` (10%) of the app code — so audits come in batches, about one a week, rather than line by line. Sensitive code (the private `rules.toml`'s `[sensitive]`) doesn't wait: committed and unaudited, it's orange at once;
- at release (the release role: `[audit.release] release_rules = "fail"` in `callboard.toml`; the rules themselves from the private `rules.toml`): a full audit by an auditor `accept` takes (`human thoroughness<=2`: a person, reading line by line or more closely; `human:sam`, one person; an AI auditor's family, at a version or later, `family>=2.1`), no older than `max_age_days`, and every line since seen by one it takes; the release candidate's tag (annotated: `git tag -a`) at least `soak_days` old; no vulnerability open at `block_open` or above (`high`: CVSS 7.0 and up); and every finding's answer for main.

**A public declaration, private requirements.** With only the public half (GitHub, anyone's clone) the block says what's covered, full or partial, and what's waiting, and adds a notice that the auditor and thoroughness requirements weren't checked: a notice, never a failure, so anyone can run it. With the private repo too, it also lists the open findings and holds the release rules; and if its `rules.toml` has no `[release] accept`, or an entry it can't read, that's orange (red at release), so a requirement that isn't set doesn't go unnoticed.

**The audits page** (`python3 dev/audit.py gui`, or `a` on callboard's board while the Security Audit block is orange) does all of it without commands, on a page on this computer only: an **Overview** (what the block says, what isn't pushed yet that no audit has seen, the new record files waiting for you to commit), **Start audit** (full or partial; of your uncommitted changes, everything unpushed, everything since the last audit, this branch against main, everything no audit has seen, or files and functions you choose; by whom and how closely), **Runs** (every audit started from it: yours while it's open, an AI auditor's while it runs), **Findings** (each one's status, answer for main and fix, changed there), the **Explorer** (the app code by how it's been audited, with toggles for full or partial, the author's own audits, auditor, thoroughness and age, and each file line by line), and the **Rules** (the private `rules.toml`, checked before it's saved). Findings opens on where things stand: a light for each step (audit, fix, report, confirm, push), what the last audit recorded here, and the one thing to do next; then the findings as a table (severity, status, how found, ID, title), filtered by where each one is, how it was found and its severity, each row opening its card (what's known about it, read-only, with an ⓘ for what each part means; the fields that change the records by hand under Manual override, which a fix your assistant made doesn't need); a finding can be **mitigated** instead of fixed (lived with for now, often until something upstream changes: `dev/audit.py fixed F-… --mitigated`), confirmed by its tests like a fix and then kept on record as mitigated, never closed as fixed, for a proper fix later; **Refresh** (no AI) reads each finding's lines again, and **Have an AI check the fixes** runs an audit of just the open findings, by the model and effort picked there. It closes 30 minutes after its page is closed, once no audit is running. Started again, it comes back on the address it had (kept in `~/.cache/plexcache-dev/`, yours alone, for 12 hours), so a tab still open reconnects by itself: it says when it's lost its server, and picks it up again when it's back. It writes files and never commits.

**A person's audit** is the default: your name (kept in the private half, with how closely you read it), then either **Start reading**, which opens it on the Runs tab with what to read and the standard prompt (what to look for), for you to add each finding as you go and **Finish and record** (or Cancel), or **Already audited it**, which records a review you've already done, its findings with it, in one go. It's recorded as the code was when you started it (its fingerprints taken then, uncommitted changes too), so a change you make while you read isn't counted as seen; the record says so. Your findings are kept as you add them (the private repo's `runs/<id>/`), so you can close the page and come back.

**An AI auditor** (a plugin, `dev/auditor_*.py`) is offered beside you only when it's installed on this computer. Claude Code is one: it runs headless with your own sign-in, as the model its auditor id names, at the effort its thoroughness is, with the standard prompt, in a copy of the code as it is now and main's beside it, able only to read (no shell, no edits, no web, never the private repo); its answer is checked and recorded as `record` would. `python3 dev/audit.py run` starts one from a terminal. Its settings, when it needs any, are `[auditors.<id>]` in the private `rules.toml` (which models it offers, where it's installed); every run is logged in the private repo's `runs/<id>/`.

**Findings** are of two kinds. A **vulnerability** is exploitable: it's scored with a CVSS 3.1 base vector (the page has a picker for it), and its severity is the score's rating. **Hardening** is a weakness that isn't exploitable as the code is now (CVSS would score it 0.0): it has a priority (low, medium, high) instead, is tracked like any other, and never holds up a release. Each finding keeps the fingerprints of its lines, so the Findings tab and the block say whether its code is still there, has changed, or is gone, against your working copy as it is (uncommitted changes too; Re-check after an edit). Gone isn't fixed. On each finding: **Mark as fixed** (your word for it: where the fix is, and its commit, are worked out from git; until it's pushed the finding and the block say so) and **False positive** (still kept, and counted).

**Fixing them.** Tell whoever fixes them (you, or an AI assistant) "Fix the security findings: run `python3 dev/audit.py fixes` and do as it says" (the Findings tab has the line to copy). `fixes` prints the open findings and how to fix them: one at a time, each with a test that would have caught it (where it fits, one that catches the same kind of problem anywhere in the code), reporting each as it goes with `dev/audit.py fixed F-YYYY-NNN --test TestClass.test_name --note "…"` (or `--attempted`, `--not-real`). Another case such a test finds isn't fixed there and then: it's reported with `dev/audit.py found --via F-YYYY-NNN …`, a new finding **found by a fix's test** (`source = "fix-test"`, `via` the finding whose fix it was), kept in that finding's audit record but never counted as found by that audit or its auditor; at the end the fixer says how many there are and asks whether to fix those too. The Findings tab follows along as it happens: a fix reported moves to **Fixed, to confirm**, with the tests that guard it (`Class.test_name`, in your private records only, so the public tests never point at a finding) and the cases its test found. The fixer can't close one. **Confirm now** runs each one's guarding tests here and closes those that pass (where its fix is, and its commit, from git); one whose tests fail is open again, saying why. A close the page didn't make (Confirm, Mark as fixed, a re-check) is flagged. Then commit and push. callboard's block says how many are open and how many wait to be confirmed, and warns if a guarding test is ever removed from tests/.

An AI auditor can re-check them too: an audit of **the open findings** (or the open findings and everything changed since the last audit) reads your working copy, the branch as pushed and main, and says of each whether it's fixed, and whether its tests would catch it; each one it finds fixed is closed: with the commit that fixed it when that's pushed, and otherwise listed as fixed, not pushed yet (on the Findings tab and in the block) until you push it. Each check is kept with the finding. A finding you decide not to fix is **accepted**, and only you set that.

**The author's own audits.** A review by the code's own author, while they build it, is recorded as a partial audit with `record --author` (private, like any other). An author audit counts for the dev rule, so the board stays green while you build, and never at release, however thorough: the one who wrote the code shares its blind spots. The Explorer can leave them out.

**From the command line:**

```sh
python3 dev/audit.py next                   # what most needs an audit, file by file: sensitive first, then the longest waiting
python3 dev/audit.py start                  # the standard prompt (the private PROMPT.md) for a full audit of this commit
python3 dev/audit.py start plexcache/peerlink.py plexcache/app.py:login    # …or a partial one
# run the audit, then fill in a copy of the private repo's templates/audit.toml
python3 dev/audit.py record filled.toml     # checked, fingerprinted, split: security/audits/<id>.toml here, audits/<id>.toml there
```

`record` also fills in the audit's `prompt` (the standard prompt's version: a hash of its text, each version kept in the private repo's `prompts/`) and each finding's `introduced_in` (the commit that brought it in, from `git blame`) and `missed_by` (the earlier audits that read those very lines, from their fingerprints, and didn't report it; a finding a fix's test found gets one too). Each finding on the audits page says what missed it, and the Overview's "Who found what, and what they missed" counts them by auditor, thoroughness and prompt version (v1, v2…), so you can see, over time, which finds and which misses. Re-check the code works it out again for older records. Then commit both halves, each in its own repo.

## Python and the other dependencies

The code needs Python 3.15 or later. The image is built on `python:3.15-slim-trixie` (`PYTHON_TAG` in the Dockerfile), whatever 3.15.x is newest at the build, and the build workflow rebuilds the release weekly so a new patch release or Debian package reaches the image within a week. MKVToolNix comes from its own repository (mkvtoolnix.download, which is why the image is Debian), ffmpeg built from its release with no external libraries (the optimizer only copies streams, hashes them and reads cover art; the static builds around carry every codec library, and Debian's package 500 MB of dependencies), oxipng from its releases and jpegtran built from libjpeg-turbo's, each pinned in the Dockerfile. GitHub runs the tests on 3.15 with every deprecation warning an error, and the Python validation after them (`callboard/typecheck.py`: `pyright`, whose `pyrightconfig.json` makes an error a fault that would fail at run time and keeps the annotation warnings at zero, and Ruff's lint, `ruff.toml`, kept at zero too).

**Kept current by a check, not by memory.** `python3 dev/upkeep.py` (and callboard's last box, which runs it): once a day it asks upstream for the newest release of everything the app depends on — the Python and the Debian the image is built on, MKVToolNix, ffmpeg, oxipng, libjpeg-turbo, pyright and Ruff (a Ruff minor release is a prompt, since its minors change what its rules find), and the Node LTS and packages that check and build the CSS, scripts and pages (`dev/package.json`, moved with npm so its lock moves too) — against what the project pins. Home Assistant is one too: for each new release, every key the MQTT discovery messages use (`DISCOVERY_KEYS` in `plexcache/homeassistant.py`, held to what's published by `test_discovery_keys_are_listed`) is looked for in that release's MQTT sources, still taken and not deprecated or removed, and `HA_CHECKED` moves to it; a key it no longer takes is a prompt naming it. A pin a patch or minor release behind is moved there and then — in a checkout of `dev`, which carries the newest software, or of `main`, which takes only minor and patch releases (a major is never looked at there: majors are only taken on `dev`, and reach `main` when it's released); on any other branch, or in a copy, it's reported — the Dockerfile or workflow edited, said in the output (MKVToolNix's every release counts as minor, since each carries fixes); a major release, or a new Debian or Python, fails the test naming it, until it's moved or held by choice. `--report` moves nothing, `--fresh` asks again. `test_dependencies_are_current` (by hand, not on GitHub) reads only the last look's answers, however old, so the suite never waits on upstream or npm: it fails on what's left to you (on `dev`, a major; on `main`, nothing, since its minor releases move by themselves; elsewhere, anything behind), and skips until there's been a look. The GitHub Actions and the image's base are Dependabot's, on `main` (with its security updates) and on `dev`. `python3 dev/versions.py` prints what an image carries; each build logs it.

**Coverage.** The tests are held to how settled the code is, not to one number for everything; git knows how long each line has stood (`git blame`), so nothing is marked by hand. *Fresh* code — not committed, or changed in the last `fresh_days` (14) — needs a test to reach each function (or server route, an `if path == "/…"` branch) it's in, and nothing more: one test at its seam while it's still moving. *Settled* code — unchanged for longer — needs `settled` (98%) of its lines run by the tests; under that, the lines no test runs are listed by file. At release (`[coverage.release]` in `callboard.toml`, the code on main or tagged a release candidate), `every_line` (98%) of every line and `each_file` (90%) of each file's, red when it isn't met; in diff mode, `changed` (90%) of the lines changed since the gate's base. The numbers are the file's, not the tool's. What counts as code: every line that holds some, but docstrings, `def` and `class` lines (they run on import) and the `if __name__ == "__main__":` tail; nothing else is left out. `python3 tests/run.py --coverage` gathers it from every worker as the suite runs (`sys.monitoring`, every thread, each line watched until it first runs), into `~/.cache/plex-cache/coverage.json`, for that code only. The optimizer's tests that need MKVToolNix and ffmpeg run only where they're installed (inside the image on GitHub), so without them the optimizer's lines count as not run.

**Translations.** The catalogs (`plexcache/web/i18n/<code>.json`) map each English text to its translation; the app shows English for anything still `null`, so a half-done language is safe to run. Between releases they may lag the code — the Translations block only tells how far they are, one number across every language. At release (`[i18n.release]` in `callboard.toml`: the code on main, or tagged a release candidate) main must ship complete: `dev/i18n.py --callboard` then fails on anything untranslated, as the file's targets say (a target per language, group or `"*"`). For a release: `python3 dev/i18n.py sync` brings every catalog in step with the code, translate what's `null` (`missing`/`merge` help), and `python3 dev/i18n.py status` says how far each language is.

**Known vulnerabilities.** The same look (`dev/upkeep.py`, callboard's Dependencies box) asks for the CVEs in what the app runs and is built with, once a day: OSV for the npm packages of `dev/package-lock.json` (and what pulls each in) and for oxipng, NVD for the ffmpeg, libjpeg-turbo and MKVToolNix the image builds, and Trivy (`dev/tools.toml`) for the image of the copy being checked, built here from it as `plex-cache:cves` (callboard's copy: `callboard main` main's, `callboard dev` dev's, `callboard local` your folder on its branch; the pins and npm lock are that copy's too). With Docker not running or the build failing, the image that copy's branch publishes instead, `dev` on dev and `latest` on main, said in a note (both when it isn't a checkout; their Debian packages, and the Python packages the base image carries; a private image needs `docker login ghcr.io`). A CVE is never a failure: one that needs doing turns the box yellow, with what to do. Only what needs doing is said: a fix a minor or patch release brings is moved as usual, its line saying what it fixes; a Debian or base-image fix is left to the weekly rebuild, and said only when the image still lacks it 8 days after it's first seen; a fix only in a major release, or in a version held by choice, is yours; a fix in a package another pulls in, that still asks for the old one, is said after 90 days (an npm override, a newer parent, or replacing it); no fix at all is upstream's while they're at it, and said once there's been none for 90 days, or no release for a year: replace it, patch it ourselves, or move to a maintained fork. A fix NVD gives only as a date in upstream's git (a snapshot range, no release named) is checked against when the release we have was tagged: made after it, it has the fix and isn't said. An image on another OS than the Dockerfile's (`latest`, built from an older one) is told its next build fixes it, not `apt-get`; and once the Dockerfile takes pip out, its packages' CVEs say the next build drops them. Both are listed apart, as fixed in dev and waiting on the release: notices, not counted, the box not orange for them. The day's answers are kept per version of `dev/cves.py`'s code (not its `DECISIONS`), so a change to it asks again the same day. A Debian CVE with no fix is Debian's call: counted, not listed. Once one's been decided, `DECISIONS` in `dev/cves.py` (the maintainer's only) records the choice, the date and why; it's looked at again after six months. On GitHub the image job checks the image it just built (`python dev/upkeep.py --cves plex-cache:test`): each one a warning on the run, never a failed build.

**The future track.** `python3 dev/future.py` builds the image on the next Python's newest prerelease (`python:3.16.0a1-slim-trixie`, say, while the image runs 3.15) and runs the whole suite inside it with every warning an error. The tools come the same way: for each, upstream's newest pre-release when it's ahead of the stable release, else that stable release — Python's alphas, betas and rcs as Docker Hub tags them; Node's nightlies and rcs from nodejs.org (the page tests need node; the image serves no pages through it, so the build is fetched once, kept in `~/.cache/plex-cache/node/`, and mounted into the container); ffmpeg's git snapshot, built from source once a week (`FFMPEG_SOURCE` and `FFMPEG_STAMP` in the Dockerfile); libjpeg-turbo's and oxipng's GitHub pre-releases; every package `dev/package.json` pins (both sections) at the newest npm dist-tag ahead of `latest` (`next`, `beta`, `rc`…), else `latest`, installed in a copy of `dev/package.json` kept in `~/.cache/plex-cache/web-future/` and mounted over the checkout's `node_modules` (yours stay at the pins; a pre-release outside another package's peer range is installed with `--legacy-peer-deps`); MKVToolNix has releases only. The web's checks run a year ahead too: the software tried is about a year ahead of the image's, so `dev/web.js` takes `"futureBrowserslist"` (`last 4 years`) in place of `"browserslist"` (`PLEXCACHE_WEB_TARGETS=future`). The run starts with a table of what it chose, kept for a day in `~/.cache/plex-cache/future.json` (`--fresh` asks again; `python3 dev/upkeep.py` reports it too); upstream not reached means the pin. `--stable` keeps every tool at the Dockerfile's pin, with Debian's node; `--tag 3.15-slim-forky` will try the next Debian the same way. The build shows as one line that moves (its step, what it's doing, the time); its full output goes to a log, shown when the build fails, or on the terminal with `-v`. The suite then runs through `tests/run.py`, with its progress bar. It needs Docker with a running engine, and uses BuildKit when Docker has it (`docker buildx`; on a Mac, `brew install docker-buildx`, then the `cliPluginsExtraDirs` line brew prints in `~/.docker/config.json`), else Docker's legacy builder. `--local` uses a `python3.16` of your own (or `uv`, which fetches prerelease builds). It is local on purpose: GitHub shows how the app runs; this shows where it is going. When the next Python is released and the suite is clean on it, moving the image is `PYTHON_TAG` in the Dockerfile and `python-version` in `build.yml`.

## Troubleshooting

- **"can't SSH to …"** — SSH isn't running on TrueNAS, or your key isn't on `truenas_admin` (step 1.2).
- **Copied, but the restart failed** — `/usr/bin/midclt` isn't in the user's no-password sudo commands (step 1.3).
- **The test app won't start after installing** — the code folder was empty: run `callboard push local`.
- **Tests fail only on your computer** — the suite has to pass on your own Python as well as the 3.15 in the image (the code needs 3.15 or later; `dev/future.py` tries the next Python's prerelease), and a system other than Linux (macOS, say) has no `/proc` and lacks some Linux-only calls (such as `os.posix_fadvise`): tests that touch those need to fake them or work without them.
