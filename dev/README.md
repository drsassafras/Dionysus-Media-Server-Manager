# Developing Dionysus

This folder holds what you need to try changes on a real TrueNAS before pushing them:

| File | What it is |
|------|------------|
| `compose.dev.yaml` | A **test copy** of the app (`plex-cache-dev`, port 8643) that runs the published image but with its code replaced by whatever you last copied to the NAS. It has its own settings, so it never touches the real `plex-cache` app. |
| `future.py` | Builds the image on the **next** Python's prerelease (3.16 while the image runs 3.15) and each tool's newest pre-release where one is ahead of its stable release (Node's nightlies, ffmpeg's git snapshot, libjpeg-turbo's and oxipng's pre-releases, the web's npm packages' `next`/`beta`/`rc` tags; MKVToolNix has releases only), and runs the suite inside it, every warning an error and the web's checks a year ahead (four years of browsers); `--stable` keeps the tools at their pins, `--local` uses an interpreter on your computer instead. The "future" track, local only (below). |
| `upkeep.py` | The dependency check: everything the app depends on against upstream's newest release, pins a minor behind moved (only with `dev` checked out), a major behind a prompt. callboard runs it on every run (below), with a progress bar for each look-up and npm install; the suite's test reads its last answers, never upstream or npm. |
| `cves.py` | The dependency check's CVEs (`upkeep.py` runs it, alongside the versions): what needs doing only, always a warning. See **Known vulnerabilities** below. |
| `versions.py` | Prints what an image carries (its OS, Python, MKVToolNix, ffmpeg…); each build logs it. |
| `codecs.py` | Codec names as MKVToolNix shows them, for Library Health (`plexcache/codec_names.py`). The image build runs it for the MKVToolNix release it installs; run it by hand to refresh the committed copy. |
| `web.js`, `package.json`, `jsconfig.json`, `web.d.ts` | What checks and builds the web app's CSS, scripts and pages: **Stylelint**, **ESLint** and **html-validate** on the source (each with a check that no feature it uses is missing from a target browser), **TypeScript** on the scripts (checkJs), **axe-core** on every page as the demos draw it (through **Playwright**), then **postcss-preset-env** (the newer CSS its targets lack, rewritten as CSS they read), **Autoprefixer** (the browser prefixes they need), **cssnano**, **Terser** and **html-minifier-terser** (minified) for the image. The settings, the browser floor and the pinned packages are in `package.json`; see below. |
| `screenshots.js` | Makes the README screenshots from the demo (see below). |
| `icons.js` | Draws the app's icons in Chromium, as a browser draws them, each from the logo the app shows at that size and centred on what it draws: `favicon.ico` from the tab icon (`plexcache/web/theatre-tab.svg`: Joined D at 16px, Wide bar at 32 and 48px; for browsers without SVG favicons), and from the full theatre playing (`theatre-playing.svg`, the menu's logo with its arrow lit) on the menu's colour the iPhone's `apple-touch-icon.png` and the installed app's `icon-192.png`, `icon-512.png` and `icon-maskable-512.png` (`manifest.webmanifest`); and the dev pages' tab icon, the film reel as `decor.js` draws it for a tab (`PCDECOR.tab`: five round holes at 16px, plain columns in the cut ring at 32px, the reel itself from 64px) in Dionysus's film colour with light cutouts, as `dev/reel-tab-*.svg`. Run `NODE_PATH=$(npm root -g) node dev/icons.js` after changing either logo or the reel, then the style sample; `IconTests` fails when one is out of date (`node dev/icons.js check`). Needs Playwright, like the screenshots. |
| `style.py`, `style-guide.json`, `style-sample.js`, `decor-draws.js` | **The style guide**: every look the app may wear, each approved by the maintainer from a sample. `style.py check` lists what's new, changed or gone (the suite fails on it), `sample` photographs those in each theme and mode, `approve` (the maintainer only, at a terminal) adds them. See below. |
| `make_fixtures.py` | Makes the optimizer's test files (`tests/fixtures/*.mkv`: many real-world features, a few hundred KB) and the snapshot of what optimizing them gives. Run it with `--snapshot` after checking a change the tests caught (needs ffmpeg and MKVToolNix). |

**callboard itself is a project of its own** ([github.com/drsassafras/Callboard](https://github.com/drsassafras/Callboard), checked out beside this one: `~/Code/Callboard`), installed once on a computer and used by every project. Its board, rules, check tools and UI used to be files of this folder; what's left here is what's Plex Cache's own, built on it (`dev/__init__.py` finds the install: `CALLBOARD_HOME`, else the `callboard` on your PATH, else `../callboard`). `callboard tool <name>` runs one of its tools in the project you're in (`callboard tool typecheck`, `buildcheck`, `coverage`). In that project:

| File | What it is |
|------|------------|
| `bin/callboard` | A small script that **copies your code to the NAS, restarts the test app and runs the tests and checks** — in one command, from your computer, all at once on a live board (`board.py`). Each run leaves a record that the callboard UI shows (below). |
| `callboard/devui.py`, `devui.html`, `devui.css`, `ui/` | **The callboard UI** (`callboard ui`): the board in your browser, a page behind each block with what its tool found, and buttons that run callboard again. See **The callboard UI** below. It wears the app's themes from a copy of its own (`ui/`, taken again with `ui/refresh.py` when the app's look moves on). |
| `callboard/devpage.py` | What the dev tools' pages share (the UI's, the audits', the style review's): served to this computer only, to the browser that opened the printed address only, closed when the page is; and their tab icon, the film reel (`reel-tab-16.svg`, `-32.svg`, `-64.svg`: one link a size, so the browser takes the one drawn for the size it shows). |
| `callboard/progress.py` | The progress bar the dev tools share, the result line, and `detail`: a tool's own account of what it found, written as JSON for its page in the UI when the board asks (`CALLBOARD_DETAIL`). |
| `callboard/typecheck.py` | **Python Validation**: pyright's type check (`pyrightconfig.json`) and Ruff's lint (`ruff.toml`), each at its version in `tools.toml`, as callboard and GitHub run them; `--fix` makes Ruff's safe fixes first. |
| `callboard/checks.py`, `tools.toml` | **What every check tool shares**: `tools.toml` holds each check tool's version (this project's own `dev/tools.toml` wins over the one callboard ships, so its pins are the ones `upkeep.py` moves) (and, for a release binary, where it comes from and its checksum for each platform); `checks.py` fetches each at it the first time (into `~/.cache/plex-cache/tools/`: `callboard.toml`'s `[config] cache`), says what each finds one way (`file:line:col - severity: message (Tool CODE)`, annotated on GitHub), draws the board's bar and says the result line. A check tool is a section of the board run through it, never one of its own (`CheckToolTests`). |
| `callboard/buildcheck.py` | **Build Validation**: ShellCheck on the project's shell scripts (every one it has; in callboard's own project, `bin/callboard`), actionlint on `.github/workflows` (with ShellCheck on each step's script) and hadolint on the `Dockerfile` (`.hadolint.yaml`), each at its version in `tools.toml`, as callboard and GitHub run them. |
| `callboard/coverage.py` | **Coverage**: how much of the code the tests reach, held by how settled it is (`git blame`): each fresh function and route reached by a test, settled code at 98%, and the release bar (98% overall, every file 90%). Through `checks.py`; no installs needed. |
| `callboard/policy.py`, `plan.py`, `board.py`, `gate.py`, `notes.py` | The rules (`callboard.toml`, read for every tool), the plan of a run, the board that draws it, the gates, and the change notes and manual release items the Gates page and `release.py` share. |

The loop is: edit on your computer → `callboard push local` → refresh `http://<nas-ip>:8643`. Nothing reaches GitHub (or the real app) until you commit and push.

## What callboard does

```
callboard [<code>]         check that code: the tests and checks, and how the NAS stands beside it (in sync, or how
                          many files are out). Nothing is copied; p on the board pushes it while the checks run
callboard push <code>      push it: copy it to the NAS and restart the app (always, files to copy or not), the checks alongside
callboard restart          restart the app, copying nothing
callboard status [<code>]  how the NAS stands beside that code (--json: as JSON, what the UI's Connected to shows)
callboard init             set up callboard for a project: its callboard.toml, to commit, and the pre-push hook if you want it
callboard gate <name>      the checks as git's event meets them (push, merge, release), the same as GitHub runs
callboard hook install     a pre-push hook that runs a push's checks (callboard hook remove takes it out)
callboard config show      every integration's rules as they stand for this code (callboard config show)
callboard ui               the callboard UI: the last run in your browser, a fresh scan of the checks, Push and Restart

<code> (local when it's left out):
  local      your folder as it is now (uncommitted changes included)
  master     the latest code on GitHub's default branch (main or master)
  dev        the latest code on GitHub's dev branch
  release    the newest release tag, e.g. v1.2.0
  beta       the newest tag including pre-releases, e.g. v1.3.0-beta.1

  -n  dry run: list what a push would copy and run the checks, change nothing
  --tests-first  push nothing until the checks have passed (with push, or p on the board)
  --skip-tests   don't run the tests and checks
  --skip-future  run the current tests only, not the future ones
  --gate <name>  the checks as git's event meets them (push, merge, release: the gate its branch or tag belongs to),
                 in diff mode where the run says so: only what changed since its base
  --focus <gate> the gate the board is coloured by (dev, stable, release; left out: the gate the code belongs to)
  --diff         diff mode on its own: only what changed since the branch's upstream
  --no-sample    Wardrobe only checks: no sample of the looks waiting is made (r makes it first then)
  --checks-only  the checks alone, nothing copied (what the UI's "Run the checks again" runs)
  --only <id>    one block alone, by its id in callboard.toml: unit, future, dhtml, types, build, coverage, audit, i18n,
                 release, upkeep, style…
  --sync-only    with push: the push alone, no checks (the UI's Push)
```

Everything runs **at the same time**, each step in a section of its own on a board about half a screen tall (`callboard/board.py`), redrawn as it goes: a block that's blue while the step is under way, then green (passed), orange (a warning: stopped with Enter, dependencies behind or CVEs to act on), red (failed) or grey (for the record: skipped, not run, already in sync): a header, its progress bar (the one it moved last) (`callboard/progress.py`'s, the same bar each tool draws on its own, sent to the board: `PLEXCACHE_PROGRESS=feed`) and the last line it printed. 

On top, the board's header: what's checked (`Local Copy on Dev`; `Committed Copy on Main` or `on Dev` for `master`/`main` and `dev`, `Release Copy of v1.2.0`, `Beta Copy of v1.3.0-beta.1`), the gate the board is coloured by and why (`· Dev`, `· Stable`, `· Release (v1.2.0-rc.1)`: what its checks are held to, below), the run's modes (`· Diff`, `· Tests first`, `· Dry run`), the commit (`a1b2c3d`, `+ uncommitted` when your folder has changes; the first thing cut on a narrow terminal) and the time since the board started, which stops when the last block ends. Under it, the keys (`[Enter] Cancel`, `[u] Open the callboard UI`, and `[r] Review Style Changes` while the style review is offered) and, on the right, how many blocks are done (`6/8 done · 1 failed`, the failed and warnings only when there are). One letter of each block's title is underlined while the board runs: pressing it opens that block's page in the callboard UI (below).

Every block reads the same way: its title, its status in capitals and its time; its bar (`done/total` and the item under way or what it did, with how many workers do it on the right, under the time); and one result line (`callboard/progress.py`'s `result`: facts joined with ` · `, no time, no workers and no count the bar already shows, so a passing suite's says what it ran on — `Python 3.15.2 · Node 26.12.0 · …`, a nightly's build stamp left off — and a failing one `3 failed · …`).

**What's on the board, and what each block is held to, is the project's `callboard.toml`** (at the root, committed; `callboard/policy.py` reads it, and `callboard config check` says whether it's well formed). Its `[integrations]` table lists each block in the order it's shown — its title, its kind (which tool's rules it follows: `tests`, `checks`, `coverage`, `audit`, `i18n`, `release`, `upkeep`, `style`), the command that runs it, the blocks it waits for (`after`) and the files it needs (`needs`) — and one that's switched off (`enabled = false`) or not set up (no command, or a file it needs missing) is hidden everywhere but the UI's Integrations page. The letter that opens each block's page follows the menu: the first free letter of its title, Hub and Sync first (so `h` is the hub, `s` the sync, `u` the unit tests, `f` the future tests, `d` DHTML, `v` the Python validation, `b` the build, `c` coverage, `e` the security audit, `t` translations, `l` the release checks, `n` dependencies, `y` style approval; `p`, `a` and `r` are the board's own), unless the integration asks for one (`letter = "x"`).

Under each integration's id are **its rules**, gate by gate: what each thing it finds is — a failure (`"fail"`: red, the run fails), a warning (`"warn"`: orange, said but nothing stopped), only told (`"info"`: grey) or ignored (`"off"`) — and its numbers (a threshold such as `settled = 98`, a window such as `fresh_days = 14`, set in `[<id>]` itself). The gates are where the code is in its life, **Dev**, **Stable** and **Release**, and `callboard.toml`'s `[gate.<name>]` tables say what belongs to each: here `dev` (and every branch no other gate lists) and alpha tags are Dev's, `main` is Stable's, and the release, release-candidate and beta tags are Release's (a beta's failures shown as warnings: `warn_tags`). A push and a pull request (the branch it goes into) are held to the gate of their branch, a tag to the gate of its kind. The rules cascade, Dev first: `[<id>.dev]`, `[<id>.stable]`, `[<id>.release]`, each saying only what it changes of the gate before it (`"off"` drops a rule), and an integration is at every gate from the first it has a table for. So a run on `dev` can't fail on what only a release needs (the release checks and the translations only tell there), and the same code on `main`, or tagged as a release candidate, is held to that gate's rules — worked out once, by callboard, from the code being checked (`CALLBOARD_RULES` and the rest of the context in each block's environment), so the board, the UI, the tools run by hand and GitHub can't disagree. No tool decides a level or a number itself: each holds only a schema of its settings, and reads the file. A rule not set is off. `callboard config show` prints every integration's rules as they stand for the code; the UI's Config tabs show and save them (below). `callboard/starter.toml` is what `callboard init` writes for a new project. **A rule is never loosened to make a check pass** (`CLAUDE.md`): the code is fixed, or the maintainer asked.

A check says what it found and exits by the worst of it: 0 passed, 1 a failure, 2 it couldn't run, 3 only telling (grey, `IN PROGRESS`), 4 a warning (orange), 5 not set up — the same for every block (`callboard/checks.py`, which every check tool goes through; its note beside the block's title is the tool's).

1. **Tour**, the sync to the NAS — on a push, copies only what changed with rsync over SSH (a bar of the files as they go), and deletes files on the NAS that you deleted locally. Installed packages (`node_modules`, from `npm ci`) never go: the NAS runs the source as it is. It then **restarts the test app** with TrueNAS's own `midclt call app.redeploy plex-cache-dev`, and waits until TrueNAS says it's done: you can refresh the page and try your change while the checks run. A push always restarts, even with nothing to copy: the app reads its pages and scripts from disk as they're asked for, but its Python only when it starts, so a copy without a restart leaves it running half old code (a new page, yesterday's `/theme.js`). On a check (`callboard local`), the block only says how the NAS stands — `already in sync`, or `out of sync: 12 files to push · 9 changed · 2 new · 1 to delete` — and `[p] Push and restart` on the board's header pushes this code there and then, the block running the push while the checks go on (with `--tests-first`, once they've passed). When a push's restart failed, a check says the app hasn't been restarted since the copy, and p (or the next push) restarts it.
2. **Unit Tests** (`unit`: `python3 tests/run.py --coverage --exclude WebCheckTests --exclude StyleGuideTests`; its rules `failures`, `warnings`, `skipped` — a warning the run printed only tells on dev, fails at release: `--coverage` saves what of the code they ran, every worker's, for the Coverage block), on exactly the code it copies (for `master`, `dev` and the rest, a copy from git, with your folder's installed packages linked in for the web tests; it installs those itself first, `npm ci --prefix dev`, when they're missing or `dev/package-lock.json` has changed).
3. **Previews**, the future tests (`future`: callboard's Previews integration, by this project's own route: `callboard tool previews -- python3 dev/future.py --exclude StyleGuideTests`; off at release, never a release's concern: the same suite on the next Python, see below: a bar for the image build, then one for the tests), stopped as soon as a unit test fails (`stop_with = ["unit"]`; the unit tests run on to their end, so every failure is still listed). `--skip-future` leaves them out when you're in a hurry.
4. **DHTML** (`dhtml`: `callboard tool webcheck`, callboard's own web check: Stylelint, ESLint, TypeScript, html-validate and axe-core, each a tool of the block's with its own findings; its bar the files checked), on `plexcache/web` and on what the app makes (`[dhtml]` in `callboard.toml`: `folders`, `package = "dev"` for the settings and packages of `dev/package.json`, `plan = "python3 tests/webplan.py"` for the server's script, every page as drawn, and the pages axe-core draws). The build's own tests (`WebBuildTests`) run with the unit tests.
5. **Python Validation** (`types`: `callboard tool typecheck`, as GitHub runs it; its bar the files checked): pyright's type check (`pyrightconfig.json`, `--warnings`: its standard rules, on the app, the dev tools and the tests, a type-ignore that no longer does anything included) and Ruff's lint (`ruff.toml`: unused imports and variables, likely bugs, older syntax Python 3.15 says more simply, the import order, the security rules), at once, each at its version in `dev/tools.toml`, through the check tools' shared code (`callboard/checks.py`). Its result line says what each found (`0 errors · 0 warnings · 0 Ruff findings`). Ruff is installed the first time, at its pin, into `~/.cache/plex-cache/tools/ruff-<version>` (nothing goes into your Python); `callboard tool typecheck --fix` makes Ruff's safe fixes (the import order, unused imports) in your folder, then checks. A rule that's wrong for a line is said so there (`# noqa: <code> — why`).
6. **Build Validation** (`build`: `callboard tool buildcheck`, as GitHub runs it; its bar the files checked): what builds and ships the app — ShellCheck on any shell script the project has (callboard's own script is checked in its project now), actionlint on the workflows (with ShellCheck on each step's script), hadolint on the `Dockerfile` — at once, each at its version in `dev/tools.toml`, fetched the first time into `~/.cache/plex-cache/tools/` (checked against the checksum there). Every finding counts, notes and style too, kept at zero: a rule wrong for a line says so there (`# shellcheck disable=SC… # (why)`), and a rule is only turned off in `.hadolint.yaml` with the maintainer's say, its reason beside it (DL3008, pinning apt packages: the image takes Debian's newest patches on purpose).
7. **Coverage** (`coverage`: `callboard tool coverage --callboard`), once the unit tests have passed, from what they saved (nothing is run again): green when every rule is met, orange with what's missing — a warning on dev, like the looks to approve: it neither stops the copy nor fails the run. At release (`[coverage.release]`), the bars of the whole codebase (`every_line`, `each_file`) are a check like the others: red when they aren't met. See **Coverage** below.
8. **Security Audit** (`audit`: `callboard tool audit`, when Ghostlight is on this computer and `ghostlight.toml` is there): what `ghostlight check` reports — which app code no security audit has seen, and the open findings — green when every rule is met, orange for a warning that neither stops the copy nor fails the run. At release its release rules are a check like the others: red. See **Security audits** below.
9. **Translations** (`i18n`: `callboard tool i18n --callboard`): how far the translation catalogs are, overall — one number across every language (`32.9% translated · 15 languages · 3552 texts`). Each language is a unit of its own, so its bar counts the languages at their target (`0/15 languages at target`); a language whose target here is 0% isn't met until it's complete, said in grey (`32.5% translated, no target here`), never failed. On the Config tab each language's target is a row of its own: every language (`*`), then each one you add with **+ Add a language…**, and the level for one short of it. Its rule is a target per language (`targets = { "*" = 0 }`: a code, a group, or `"*"` for every language, each the share of the texts translated): between releases the catalogs may lag, so the target is 0 and the block only tells, grey, `IN PROGRESS`; at release (`[i18n.release]`: `{ "*" = 100 }`, `unused = "fail"`) every text must be translated and no catalog entry unused — anything missing is listed per catalog and the block is a failure, red, like a failing test; a preview (a beta tag) says the same as warnings. In diff mode, `present` asks that each text added since the base is in every catalog. See **Translations** below.
10. **Release checks** (`release`: `callboard tool release --callboard`), every run, as an overall readiness: everything that has to be true of a release, each its own line and its own rule (`version`, `translations`, `mqtt_settings`, `mqtt_docs`, `coverage`, `audits`, `looks`, `change_notes`, `manual`) — the version a new `X.Y.0` above what `main` and the release tags have, every translation catalog complete, every setting placed for MQTT (a control in Home Assistant, or listed in `NOT_OVER_MQTT` in `plexcache/homeassistant.py` with why it isn't one), the README's MQTT topics and commands the ones the code has, the coverage release bars met (from what the tests saved), the security audits' release rules, every look approved into the style guide, at least one **change note** written since the last release (a file under `changes/`, `notes_dir`: one per change, written as the work goes; the GitHub Release's notes are made of them, `callboard tool release notes`), and every **manual item** ticked for the version (`manual_items`: what a person does for a release, ticked on the UI's Gates page or with `callboard tool release tick <item>`; the ticks are kept under `changes/`, to commit). Each requirement is a unit of its own, so its bar counts them: `3/9 requirements met`, a miss held as fail counted red, as warn orange, as info neither (the bar's grey rest). Between releases it only tells: grey, its line the readiness (`4 of 9 ready · to go: version, translations, coverage`). At release — the code on `main`, or tagged a release candidate (`callboard tool release candidate`) — every rule is `"fail"`: red when it fails, what it found printed above the board, and with `--tests-first` nothing is copied; a preview (`callboard tool release start`: a beta tag) says the same as warnings. `callboard release` is something else: the newest release tag synced.
11. **Dependencies** (below).
12. **Wardrobe**, the style review (`style`: `callboard tool style check`; `waiting = "warn"`: the looks waiting for your approval, see "The style guide" below), on its own: green when every look is approved, orange when some wait, its block saying how many and the command to approve them (`callboard tool style review`, which makes the sample again first when the page is out of date). When looks wait, the block then makes their sample there and then (`callboard tool style sample`, its bar on the block: `LOOKS WAITING: MAKING SAMPLE`; the pages photographed several at once, its workers beside the bar), in your folder, so the review opens at once; one that can't be made leaves the block `LOOKS WAITING: NO SAMPLE`, what it said above the board, never a failure. Only one sample is made at a time: a review or sample started meanwhile waits for it. `--no-sample` leaves it to the check alone, as it was: no sample, no review at the end. Once it's made, the header offers **r**, and the review page opens in your browser. And once every other block is done (none failed, on a terminal, not a dry run) with looks still waiting, the review is the block's last step on the board: blue `IN REVIEW`, the page's address its line, the board kept up until you close the page (Enter skips it: `LOOKS WAITING` again); then the check again, and the block ends green `ALL APPROVED` (`6 approved just now · commit dev/style-guide.json`) or yellow with what's left. Once they're done, the block says the command instead. Nothing it found is printed above the board; it doesn't hold up the copy (`--tests-first` included) or the future tests, and its warning isn't a failure. It's the last block on the board, and runs every time, even on code that already passed, since it's quick.

Each section keeps the same three lines from the start, its whole block in its colour, so nothing moves as it fills in; when a step ends, its result is in its own block, and nothing is said again after it. What a failed step printed (the tests' failures in full), and the dependencies' box when they aren't all current, go *above* the board as the step ends, so the board stays put at the bottom of the screen: scroll up to read them. Enter stops the checks (a copy under way finishes). The test app is already running that code (unless `--tests-first`), so fix it and sync again.

The **dependencies** (`upkeep`: `callboard tool upkeep --callboard`; `behind` and `cves` warnings, the CVE windows in days, and `move`: which releases it moves itself in this checkout — `"all"` on dev, `"minor"` on main, `"none"` elsewhere) are looked up in your folder rather than the copy while the rest runs; once the checks are done it runs again (from the day's answers) to move what it moves, so a pin never changes under the tests, and shows one last box: green when everything is at upstream's newest release; yellow with each package that has a new version and what to do about it (a major release is yours to move; a minor or patch one moves by itself on `dev`); grey when upstream couldn't be reached. With `dev` checked out, the minor and patch releases are moved there and then, in your folder: the box lists them, to test (the next `callboard`) and commit. With `main` checked out, only minor and patch releases count: they're moved there the same way, and a major release isn't reported at all (majors are only ever taken on `dev`, and reach `main` when dev is released). On any other branch it only reports.

**If the NAS already has exactly these files** (compared by content, so the same code from another branch counts too), nothing is copied and the app isn't restarted. If the last tests callboard ran on that code passed, the Sync block says it's already in sync and each check's block that it already passed (grey), and nothing runs but the dependencies. If they failed (or there's no result yet, `callboard.toml` changed, the last tests weren't run for this code's role or phase — a pass as dev doesn't count for the same code as a release candidate: its rules differ — or the last run was a different command such as `callboard master`), the Sync block says the files are in sync (grey) and the checks run again. The last result is kept in `~/.local/state/callboard/`.

With `--tests-first`, the copy waits for the checks, and if any fail (from the first failing test, not once the suite ends) **nothing is copied and the app isn't restarted**, so the NAS keeps running the last good code. Use it when the test app needs to stay working (for example, before syncing `master` or a release).

`master`, `dev`, `release` and `beta` copy exactly what's in git at that point; they never touch your working folder.

callboard isn't specific to this project — any project with a `callboard.toml` in its root can use it (to push, with a `[tour]`): `callboard init` writes it.

**The gates on GitHub.** Each gate's `github` says which of git's events GitHub runs there (`push`, `pull_request`, `tag`): here a pull request into `dev` or an alpha tag at Dev, a pull request into `main` at Stable, and a release tag at Release; `[github] enabled = false` keeps GitHub out of all of them until you say. `callboard gate push` (or `merge`, `release`) runs one here exactly as GitHub would (`callboard/gate.py`: the same plan, the same tools, a record like any run), and the pre-push hook checks a push against its branch's gate before it leaves; `.github/workflows/gates.yml` runs the event GitHub met, and `.github/workflows/publish.yml` the release: a version tag pushed runs the Release gate, builds and publishes the image at that version, makes the GitHub Release (its notes the change notes since the last release; a beta or release candidate a pre-release), and after a release proper opens a pull request moving `__version__` on to the next `X.Y.0` (`callboard tool release bump`). A release is started with a tag, not a flag: `callboard tool release start` tags the next beta (the Release rules as warnings), `candidate` the next release candidate (the Release rules as they are), `hotfix <name>` makes a `hotfix/<name>` branch off the release branch, and `git push origin <tag>` sets GitHub going.

**Every run leaves a record** in `~/.local/state/callboard/runs/<when>-<n>/`: the plan callboard wrote (`plan.json`: what the run is and each block's command), each block's output (`logs/`), the board's state as it went (`state.json`, rewritten as each block moves), each block's result (`results`) and each tool's detail for its page (`detail/<block>.json`). The newest 30 are kept (`CALLBOARD_KEEP_RUNS`). The UI reads them; nothing else does.

## The callboard UI

`callboard ui` (or `u` on a running board) opens the board in your browser: a **hub** with a card per block — its colour, its bar, its result line, when it last ran — and, when nothing is under way, starts a fresh scan of the checks (`--checks-only`, as the last run was: its code) whose numbers fill in as they come. It shows the run as it was last time until then, so there's always something to look at. The page follows the app's themes (Classic and Dionysus, light and dark: the pickers in its sidebar) with the app's own stylesheet; its own looks (`callboard/devui.css`) are outside the style guide, so no approval is asked for them.

Behind each block is a **page** of what its tool found, opened by its letter (on the board, in the sidebar, or typed on the page: the letters follow the menu, above — `h` the hub, `s` Tour, `u` Unit Tests, `e` Previews, `d` DHTML, `v` Python Validation, `b` Build Validation, `c` Coverage, `i` Security Audit, `t` Translations, `l` Release checks, `n` Dependencies, `w` Wardrobe; the audits and the Wardrobe review keep their own pages, `a` and `r`). Each page has the block's bar, its result last time, its tool's detail, the board's Issues for it, its output, and **Run again** (`--only <block>`: that block alone). The detail is the tool's own account, written by the tool as JSON beside the record (`callboard/progress.py`'s `detail`, in the file the board names with `CALLBOARD_DETAIL`): the page only shows it, so the board, the UI and the tool can't disagree about what happened (one source of truth: the tool).

| Page | What its tool writes |
|------|----------------------|
| Unit Tests, Previews | `tests/run.py`: the counts, each failure as unittest printed it (with the command to run it alone), what it ran on, the slowest classes. The Future page adds the channels' picks (each dependency's pre-release or stable), the image build and each part's result. |
| DHTML, Python and Build Validation | `callboard/checks.py`: each tool, its version, what it found (`file:line:col`, the rule, fixable or not) and the files it read. |
| Coverage | `callboard/coverage.py`: the totals, the rules, each fresh function and whether a test reaches it, each file's cover and the lines not run, then the checks' findings. |
| Translations | `callboard tool i18n`: how far each language is, what's wrong in each catalog, the English in `app.js` that doesn't go through `T()`, and **Export** per language: the file `callboard tool i18n missing <code>` prints (translate the values, then `merge`). The page is read-only: the catalogs change by `sync` and `merge` only. |
| Release checks | `callboard tool release`: each check as it came, its level at this gate, what to do for one that isn't met, how many are ready, the rules skipped in diff mode. |
| Dependencies | `callboard tool upkeep`: each dependency pinned and newest, what moved here, what's new upstream and whose it is to move, the CVEs as judged, the box as the board shows it. |
| Sync | the push: what went where, each file rsync listed, whether the app was restarted. |

The hub's buttons run callboard itself, one at a time, in the project: **Run the checks again** (`--checks-only`). Its **Connected to** card says where callboard pushes — the app, the NAS and its folder, and the Dionysus that answers at the app's web port (`TN_WEB_PORT` in `.callboard`, 8642 if not set): its fingerprint and identicon, as its own pages show them, from its open hello — and how the NAS stands beside the code picked there (Local, Dev, Master, Release, Beta: `callboard status <code>`): in sync, or how many files are out (changed, new, to delete), with the last push and restart. **Push** pushes the code picked (`callboard push <code> --sync-only`: copied and restarted, nothing else) and **Restart** restarts the app (`callboard restart`); beside them, a tally of how the checks stand (failed, warnings, passed, and what's still to go). The run they start writes a record like any other, and the page follows it; the card asks the NAS again once it ends (or on refresh). The hub's sub-line says the code's role or phase, the gate and the mode, as the run had them.

Its **Integrations** page lists every integration `callboard.toml` names, on the board or hidden (off, or not set up), with its letter, kind, command and what it waits for; each has a **Config** tab: the integration's rules as the file holds them — a card for each gate it's at, from its first (another added from **Add a gate**, one taken off with its ×), each with only what it changes of the gate before it, every setting a field by its kind (a level, a number with its own level, a toggle, a list, targets) with what it decides beside it — and, under them, the rules as each gate holds them once the cascade is applied (what `callboard config show` prints). **Save** writes `callboard.toml` again (the whole file, checked against the schemas first; comments aren't kept) and commits nothing: the change is in your folder, to look at and commit like any other; `[config] read_only = true` keeps the tab to showing. The **Gates** page says what belongs to each gate and what GitHub runs there, the tags and branches, the change notes written since the last release, and the manual release items, each ticked there once it's done. Its **Runs** page lists the records.

The page is served to this computer only, to the browser that opened the printed address only (`callboard/devpage.py`), and the UI closes when the page is: `callboard ui --no-browser` prints the address instead of opening it, `--no-scan` skips the fresh scan, `--port <n>` picks the port.

## Setting it up (once)

### 1. On TrueNAS

1. **SSH:** System → Services → SSH: turn it on (and tick "Start automatically").
2. **Your key:** Credentials → Users → `truenas_admin` → Edit → paste your computer's public key (`cat ~/.ssh/id_ed25519.pub`; make one with `ssh-keygen -t ed25519` if you don't have it) into **Authorized Keys**. Check it works: `ssh truenas_admin@<nas-ip>`.
3. **Permission to restart apps:** on the same user, add `/usr/bin/midclt` to **Allowed sudo commands with no password**. (callboard tries `midclt` directly first and falls back to `sudo -n midclt`.)
4. **Folders for the test app** — in the TrueNAS shell (change the paths if your apps live elsewhere):
   ```sh
   sudo mkdir -p /mnt/ssd/AppConfigs/plex-cache-dev/src /mnt/ssd/AppConfigs/plex-cache-dev/config
   sudo chown truenas_admin /mnt/ssd/AppConfigs/plex-cache-dev/src
   sudo chown 568:568 /mnt/ssd/AppConfigs/plex-cache-dev/config
   ```

### 2. On your computer

1. **Get callboard and put it on your PATH** (the tests and this folder's tools need it too: they're built on it):
   ```sh
   git clone https://github.com/drsassafras/Callboard ~/Code/Callboard   # (beside this project; once for every project)
   chmod +x ~/Code/Callboard/bin/callboard
   mkdir -p ~/bin
   ln -sf ~/Code/Callboard/bin/callboard ~/bin/callboard   # ~/bin must be on your PATH
   ```
   (If `callboard` then says "permission denied", the `chmod +x` was missed.)
2. **Your NAS's address**, shared by every project — `~/.config/callboard/config`:
   ```
   TN_HOST=192.168.1.10
   TN_USER=truenas_admin
   TN_PORT=22
   ```
3. **The test app** — `callboard.toml`'s `[tour]` (committed): where the test app is, and what's copied. A computer that needs its own lays a `[tour]` over it in `callboard.local.toml` (never committed).
   ```toml
   [tour]
   app = "plex-cache-dev"
   web_port = 8643
   dest = "/mnt/ssd/AppConfigs/plex-cache-dev/src"
   paths = ["plexcache"]
   exclude = [".git", ".DS_Store", "__pycache__", "*.pyc"]
   ```
   The NAS file is read as `KEY=value` lines, never run. The checks themselves — which run, with what command, held to what — are the project's, in `callboard.toml` too (`callboard init` writes it from `callboard/starter.toml` when there's none).

### 3. The test app

1. Run `callboard push local` once **before** installing the test app (its restart fails then: the app isn't there yet), so its code folder exists (otherwise Docker creates an empty one and the app won't start).
2. Open `compose.dev.yaml`, make the media lines match your real `plex-cache` app (and Plex), and set your NAS's IP in `x-portals`.
3. TrueNAS: Apps → Discover Apps → ⋮ → **Install via YAML**, name it `plex-cache-dev`, paste the file.

After that, `callboard push local` is all you need (or `callboard local`, and p on the board when you want it on the NAS).

## The CSS, the scripts and the pages

`plexcache/web`'s CSS, scripts and pages are written as they're read, checked against one floor of target browsers (callboard's web check: `callboard tool webcheck`, the DHTML block) and built for the image by `dev/web.js`. The floor is an age: every browser version out in the last five years (`"browserslist"` in `dev/package.json`, `last 5 years`; in November 2026 that's Safari and iOS 15.2, Chrome and Edge 96, Firefox 95 — about 97% of use). One age holds every browser to the same date, so the CSS, the scripts and the HTML can't disagree on what's supported, and the window moves on by itself: each build is checked against the browsers of its own day, so what an old browser lacks stops counting once it falls out of the window, and the pages may then use it. QQ Browser is left out (caniuse's data for it: an old engine without `min()`).

- **The CSS** is written **without browser prefixes** (`-webkit-`, `-moz-`, `-ms-`, `-o-`): write the standard property and leave the prefixes to Autoprefixer. It may use newer standard CSS that **postcss-preset-env** rewrites for the targets (nesting, the media range syntax `(width >= 600px)`, `lab()` and `oklch()` colours and the rest of its stage 2 features): the build writes them out as CSS the oldest targets read, keeping the newer form beside it where the plugin does. What it can't rewrite (container queries, subgrid, `:has()`) is held to the floor as before. Only `app.css` is built: the pages' and scripts' own styles and the themes' CSS reach the browser as written, so they keep to CSS the targets read. An old Safari throws out a whole rule when one of its selectors is new to it, so a newer selector (`:focus-visible`, `:has()`) gets a rule of its own rather than sharing one (`.x:hover{…}.x:focus-visible{…}`, not `.x:hover,.x:focus-visible{…}`); cssnano, told the targets, keeps them apart.
- **The checks**: Stylelint on the CSS, ESLint on the scripts and html-validate on the pages and on every page as the app draws it — each with its recommended checks (html-validate's `standard`), none turned off — and each with a check that nothing it uses is missing from a target: stylelint-no-unsupported-browser-features (caniuse's data), eslint-plugin-compat, and for the HTML a check of every element, attribute and input type against MDN's data (callboard's `callboard/webcheck.js`, with `dev/package.json`'s settings and packages). The CSS is checked twice: as written (Stylelint's checks, no prefixes), and as the oldest targets get it — what postcss-preset-env makes of it, the newer forms left out — for what a target lacks, each finding told by the line it's written on. So a feature the build rewrites passes, and one it can't is found. A finding is fixed in the code.
- **The scripts' types**: TypeScript checks the app's own scripts together, as they are (checkJs, not strict: `dev/jsconfig.json`), for a property that isn't there, a call with arguments nothing takes, or a value of the wrong kind. What it can't see from the code is written down in `dev/web.d.ts`: the page's globals, the element a handler's event comes from (`/** @param {On<MouseEvent>} e */`), and a card's rows (`Row`). Its ESLint rules beside the recommended ones: `no-var`, `prefer-const`, `no-shadow`, `eqeqeq` (smart: `== null` stays), `no-implicit-globals` and `no-unused-vars`.
- **Accessibility**: axe-core's standard rules, none turned off, on every page of the app as the two demos draw it (`tests/demo.py`: the showcase and the one with problems), in Classic and Dionysus, light and dark (`callboard tool webcheck --only axe`, about two minutes; the pages are `tests/webplan.py`'s). Each finding names the element, the rule, and the pages and looks it's on. A colour that fails its contrast is a look: its fix is shown in the style sample and waits for the maintainer's approval like any other. Chromium is Playwright's, at `dev/package.json`'s version (`npx --prefix dev playwright install chromium`, once), or the one `CALLBOARD_CHROMIUM` names.
- **What the pages can do without** (`"graceful"` in `dev/package.json`): the few features a target lacks that only do nothing there — a focus ring an old Safari draws its own way, a cursor on a phone, `loading="lazy"` on posters — each named with why. The checks pass over these only; a new one is a choice, and `WebBuildTests` lists them. When the window has passed one (the checks no longer find it with the entry taken out), it comes out.

The image build (the Dockerfile's `web` stage, on Node's LTS) runs `dev/web.js build` on each: the CSS gets its newer features rewritten for its targets and the prefixes they still need and is minified with cssnano, the scripts are minified with Terser and the pages with html-minifier-terser; those copies replace the source's in the image. `callboard` copies the source as it is, so the test app serves it unprefixed and unminified — fine for a current browser.

```sh
callboard tool webcheck --skip axe           # Stylelint, ESLint, TypeScript and html-validate on plexcache/web and what the app makes
callboard tool webcheck --only axe           # axe-core on every page, both demos, each look (once: npx --prefix dev playwright install chromium)
node dev/web.js build plexcache/web/app.css  # what the image ships, to stdout (--no-minify: prefixed only); a .js or .html the same
```

The suite checks it (`WebBuildTests` the build, `WebCheckTests` the checks, which run callboard's web check): no prefix written by hand in the CSS, the pages' and scripts' own styles or the themes' CSS; every check clean on every stylesheet, script and page, on the server's `/theme.js` and on every page as drawn before and after the first checks; the floor and the graceful list as they're meant to be; no newer selector sharing a rule; the CSS build clean, only adding prefixes and fallbacks (every declaration written kept, in order); the CSS check passing what postcss-preset-env rewrites and finding, by its line, what it can't; the built scripts drawing every page as the source does, and the built pages keeping every tag and word. They need `npm ci --prefix dev` (GitHub's test job runs it); without node they skip, like the page tests.

## The style guide

Every look the app wears is one the maintainer approved, and `dev/style-guide.json` lists them all: each rule of `plexcache/web/app.css` (by its selector and media query, with its declarations), each `style="..."` a page or script writes, each style property a script sets, each drawing (an icon, the grape arrow, a chart's marks), what `plexcache/web/decor.js` draws (run on a fixed page by `dev/decor-draws.js`, so a change to its code that draws the same needs no approval), each part of the themes' CSS (`themes.py`'s `css()` and `script()`), every colour, font and decoration of the built-in themes, and every image and font the app ships. `StyleGuideTests` fails on any look that isn't in the guide, isn't as the guide has it, or has gone from the code, and on a guide edited by hand (its seal won't match).

A new or changed look goes in only like this:

```sh
callboard tool style check     # what differs from the guide
callboard tool style sample    # optional: makes the page ahead (each of those Before and After, side by side); review does it when needed
callboard tool style review    # the maintainer, at a terminal: the page with Approve all and an Approve per change
callboard tool style approve   # the same at a terminal without the page: type "approve" to add them all
```

`sample` needs Playwright, like the screenshots (`npm ci --prefix dev && npx --prefix dev playwright install chromium`); it shows the dev tools' progress bar while it works. It starts two demos with the same data, today's app and the app as approved (today's with the approved look files put back: the files `approve` keeps in git, their blob ids the guide's `files`, so the Before is the app's own history and never a copy nobody can read in a diff; or a folder given with `sample --before <folder>`), photographs each look on both in Classic and Dionysus, light and dark, cropped to the same spot, and compares them pixel for pixel. The page shows only what looks different, Before and After side by side (with a button that marks the pixels that changed); a look drawn on no demo page as its code, Before and After; and, folded away, the looks whose code changed but that drew exactly the same, which need no looking at (approving still covers them). A look seen on whole pages (a theme's colour, a shipped image) is judged against its own file put back alone, so another change on the page isn't taken for it; `decor.js` can't run with another day's styles, so its looks are judged against the whole Before. When the Before itself isn't exactly as the guide has it, the page says which looks. Words aren't a look: what the app says is content, so rewording a title, a label or a tooltip needs no approval (in a look, any text with a letter in it is `…`: between tags, in the attributes people read, in a stylesheet's `content`), and the Before takes today's pages, scripts and translations for a stylesheet's rules and the whole-page looks, so a reworded title doesn't show as a difference either. Each pair has "Highlight the difference" and a slider view (full width: click or drag on the picture, or the slider under it, to move between Before and After). `review` serves that page to this computer only (127.0.0.1), and to the browser that opened the address it printed only (a one-time code swapped for a cookie, `callboard/devpage.py`; with a token the page's buttons send) while it runs, and only when started at a terminal: "Approve all", or "Approve" on one change, puts those looks in the guide (each only if it still differs exactly as the sample showed it), and an approved change leaves the page; it closes once everything is approved, or after an hour unused (`review --board` is callboard's r: what it says goes to `dev/style-sample/review.log`); once everything is approved it keeps the approved files in git too. `check` fails with how many looks wait and, on callboard's board, a line linking the page (or saying it's out of date). `approve` only takes a sample of exactly the looks that differ now (its fingerprint; change the code after and it asks for a new sample), keeps the sample's fingerprint and the date in the guide, keeps the approved look files in git (`git hash-object -w`, their ids in the guide's `files`: the next sample's Before; commit the files as they were approved, with the guide), and won't run without a terminal. Nobody but the maintainer approves, edits the guide or loosens the test (`CLAUDE.md`). A theme someone uploads on System → Themes is their own: the guide covers the code.

## Security audits

Security audits are kept by **Ghostlight**, a program of its own (`ghostlight`, with this project's settings in `ghostlight.toml`): it keeps track of what each audit saw, line by line, the findings, and the release rules. Each audit has a public half here (`security/audits/<id>.toml`) and a private half in the private audits repo (`~/Code/Dionysus-Media-Server-Manager-audits`). See Ghostlight's own README for its page and commands.

callboard's **Security Audit** block (`callboard tool audit`) says what `ghostlight check` reports, each finding held at the level `callboard.toml`'s `[audit]` gives its rule. Where Ghostlight isn't on the computer, the block isn't offered.

## Python and the other dependencies

The code needs Python 3.15 or later. The image is built on `python:3.15-slim-trixie` (`PYTHON_TAG` in the Dockerfile), whatever 3.15.x is newest at the build, and the build workflow rebuilds the release weekly so a new patch release or Debian package reaches the image within a week. MKVToolNix comes from its own repository (mkvtoolnix.download, which is why the image is Debian), ffmpeg built from its release with no external libraries (the optimizer only copies streams, hashes them and reads cover art; the static builds around carry every codec library, and Debian's package 500 MB of dependencies), oxipng from its releases and jpegtran built from libjpeg-turbo's, each pinned in the Dockerfile. GitHub runs the tests on 3.15 with every deprecation warning an error, and the Python validation after them (`callboard/typecheck.py`: `pyright`, whose `pyrightconfig.json` makes an error a fault that would fail at run time and keeps the annotation warnings at zero, and Ruff's lint, `ruff.toml`, kept at zero too).

**Kept current by a check, not by memory.** `callboard tool upkeep` (and callboard's last box, which runs it): once a day it asks upstream for the newest release of everything the app depends on — the Python and the Debian the image is built on, MKVToolNix, ffmpeg, oxipng, libjpeg-turbo, pyright and Ruff (a Ruff minor release is a prompt, since its minors change what its rules find), and the Node LTS and packages that check and build the CSS, scripts and pages (`dev/package.json`, moved with npm so its lock moves too) — against what the project pins. Home Assistant is one too: for each new release, every key the MQTT discovery messages use (`DISCOVERY_KEYS` in `plexcache/homeassistant.py`, held to what's published by `test_discovery_keys_are_listed`) is looked for in that release's MQTT sources, still taken and not deprecated or removed, and `HA_CHECKED` moves to it; a key it no longer takes is a prompt naming it. A pin a patch or minor release behind is moved there and then — in a checkout of `dev`, which carries the newest software, or of `main`, which takes only minor and patch releases (a major is never looked at there: majors are only taken on `dev`, and reach `main` when it's released); on any other branch, or in a copy, it's reported — the Dockerfile or workflow edited, said in the output (MKVToolNix's every release counts as minor, since each carries fixes); a major release, or a new Debian or Python, fails the test naming it, until it's moved or held by choice. `--report` moves nothing, `--fresh` asks again. `test_dependencies_are_current` (by hand, not on GitHub) reads only the last look's answers, however old, so the suite never waits on upstream or npm: it fails on what's left to you (on `dev`, a major; on `main`, nothing, since its minor releases move by themselves; elsewhere, anything behind), and skips until there's been a look. The GitHub Actions and the image's base are Dependabot's, on `main` (with its security updates) and on `dev`. `python3 dev/versions.py` prints what an image carries; each build logs it.

**Coverage.** The tests are held to how settled the code is, not to one number for everything; git knows how long each line has stood (`git blame`), so nothing is marked by hand. *Fresh* code — not committed, or changed in the last `fresh_days` (14) — needs a test to reach each function (or server route, an `if path == "/…"` branch) it's in, and nothing more: one test at its seam while it's still moving. *Settled* code — unchanged for longer — needs `settled` (98%) of its lines run by the tests; under that, the lines no test runs are listed by file. At release (`[coverage.release]` in `callboard.toml`, the code on main or tagged a release candidate), `every_line` (98%) of every line and `each_file` (90%) of each file's, red when it isn't met; in diff mode, `changed` (90%) of the lines changed since the gate's base. The numbers are the file's, not the tool's. What counts as code: every line that holds some, but docstrings, `def` and `class` lines (they run on import) and the `if __name__ == "__main__":` tail; nothing else is left out. `python3 tests/run.py --coverage` gathers it from every worker as the suite runs (`sys.monitoring`, every thread, each line watched until it first runs), into `~/.cache/plex-cache/coverage.json`, for that code only. The optimizer's tests that need MKVToolNix and ffmpeg run only where they're installed (inside the image on GitHub), so without them the optimizer's lines count as not run.

**Translations.** The catalogs (`plexcache/web/i18n/<code>.json`) map each English text to its translation; the app shows English for anything still `null`, so a half-done language is safe to run. Between releases they may lag the code — the Translations block only tells how far they are, one number across every language. At release (`[i18n.release]` in `callboard.toml`: the code on main, or tagged a release candidate) main must ship complete: `callboard tool i18n --callboard` then fails on anything untranslated, as the file's targets say (a target per language, group or `"*"`). For a release: `callboard tool i18n sync` brings every catalog in step with the code, translate what's `null` (`missing`/`merge` help), and `callboard tool i18n status` says how far each language is.

**Known vulnerabilities.** The same look (`callboard tool upkeep`, callboard's Dependencies box) asks for the CVEs in what the app runs and is built with, once a day: OSV for the npm packages of `dev/package-lock.json` (and what pulls each in) and for oxipng, NVD for the ffmpeg, libjpeg-turbo and MKVToolNix the image builds, and Trivy (`dev/tools.toml`) for the image of the copy being checked, built here from it as `plex-cache:cves` (callboard's copy: `callboard main` main's, `callboard dev` dev's, `callboard local` your folder on its branch; the pins and npm lock are that copy's too). With Docker not running or the build failing, the image that copy's branch publishes instead, `dev` on dev and `latest` on main, said in a note (both when it isn't a checkout; their Debian packages, and the Python packages the base image carries; a private image needs `docker login ghcr.io`). A CVE is never a failure: one that needs doing turns the box yellow, with what to do. Only what needs doing is said: a fix a minor or patch release brings is moved as usual, its line saying what it fixes; a Debian or base-image fix is left to the weekly rebuild, and said only when the image still lacks it 8 days after it's first seen; a fix only in a major release, or in a version held by choice, is yours; a fix in a package another pulls in, that still asks for the old one, is said after 90 days (an npm override, a newer parent, or replacing it); no fix at all is upstream's while they're at it, and said once there's been none for 90 days, or no release for a year: replace it, patch it ourselves, or move to a maintained fork. A fix NVD gives only as a date in upstream's git (a snapshot range, no release named) is checked against when the release we have was tagged: made after it, it has the fix and isn't said. An image on another OS than the Dockerfile's (`latest`, built from an older one) is told its next build fixes it, not `apt-get`; and once the Dockerfile takes pip out, its packages' CVEs say the next build drops them. Both are listed apart, as fixed in dev and waiting on the release: notices, not counted, the box not orange for them. The day's answers are kept per version of callboard's CVE code (not the decisions), so a change to it asks again the same day. A Debian CVE with no fix is Debian's call: counted, not listed. Once one's been decided, `[upkeep] decisions` in `callboard.toml` (the maintainer's only) records the choice, the date and why; it's looked at again after six months. On GitHub the image job checks the image it just built (`callboard tool upkeep --cves plex-cache:test`): each one a warning on the run, never a failed build.

**The future track.** `python3 dev/future.py` builds the image on the next Python's newest prerelease (`python:3.16.0a1-slim-trixie`, say, while the image runs 3.15) and runs the whole suite inside it with every warning an error. The tools come the same way: for each, upstream's newest pre-release when it's ahead of the stable release, else that stable release — Python's alphas, betas and rcs as Docker Hub tags them; Node's nightlies and rcs from nodejs.org (the page tests need node; the image serves no pages through it, so the build is fetched once, kept in `~/.cache/plex-cache/node/`, and mounted into the container); ffmpeg's git snapshot, built from source once a week (`FFMPEG_SOURCE` and `FFMPEG_STAMP` in the Dockerfile); libjpeg-turbo's and oxipng's GitHub pre-releases; every package `dev/package.json` pins (both sections) at the newest npm dist-tag ahead of `latest` (`next`, `beta`, `rc`…), else `latest`, installed in a copy of `dev/package.json` kept in `~/.cache/plex-cache/web-future/` and mounted over the checkout's `node_modules` (yours stay at the pins; a pre-release outside another package's peer range is installed with `--legacy-peer-deps`); MKVToolNix has releases only. The web's checks run a year ahead too: the software tried is about a year ahead of the image's, so `dev/web.js` and callboard's web check take `"futureBrowserslist"` (`last 4 years`) in place of `"browserslist"` (`PLEXCACHE_WEB_TARGETS=future`, `CALLBOARD_WEB_TARGETS=futureBrowserslist`). The run starts with a table of what it chose, kept for a day in `~/.cache/plex-cache/future.json` (`--fresh` asks again; `callboard tool upkeep` reports it too); upstream not reached means the pin. `--stable` keeps every tool at the Dockerfile's pin, with Debian's node; `--tag 3.15-slim-forky` will try the next Debian the same way. The build shows as one line that moves (its step, what it's doing, the time); its full output goes to a log, shown when the build fails, or on the terminal with `-v`. The suite then runs through `tests/run.py`, with its progress bar. It needs Docker with a running engine, and uses BuildKit when Docker has it (`docker buildx`; on a Mac, `brew install docker-buildx`, then the `cliPluginsExtraDirs` line brew prints in `~/.docker/config.json`), else Docker's legacy builder. `--local` uses a `python3.16` of your own (or `uv`, which fetches prerelease builds). It is local on purpose: GitHub shows how the app runs; this shows where it is going. When the next Python is released and the suite is clean on it, moving the image is `PYTHON_TAG` in the Dockerfile and `python-version` in `build.yml`.

## Troubleshooting

- **"can't SSH to …"** — SSH isn't running on TrueNAS, or your key isn't on `truenas_admin` (step 1.2).
- **Copied, but the restart failed** — `/usr/bin/midclt` isn't in the user's no-password sudo commands (step 1.3).
- **The test app won't start after installing** — the code folder was empty: run `callboard push local`.
- **Tests fail only on your computer** — the suite has to pass on your own Python as well as the 3.15 in the image (the code needs 3.15 or later; `dev/future.py` tries the next Python's prerelease), and a system other than Linux (macOS, say) has no `/proc` and lacks some Linux-only calls (such as `os.posix_fadvise`): tests that touch those need to fake them or work without them.
